# ------------------------------------------------------------------ ABSTRACT
@FRONT|ABSTRACT|Abstract

@P|Bangladeshi social-media monitoring runs on text that off-the-shelf language technology handles poorly: Bangla script, English and romanized "Banglish" mix inside single comments, and the platforms supplying it store one coarse sentiment per post and none per comment. Sending every item to a large language model is accurate but unaffordable at realistic volumes; small classifiers alone are affordable but weak on the code-mixed text that dominates the traffic. Published cost-aware cascades resolve that tension for single queries only: none routes a *thread* whose thousands of comments each need labelling, none reports what share of the bill the routing decision governs, and none carries alias-aware target stance or per-label provenance into a deployable low-resource-language system. This project builds, measures and audits a microservice that decides per unit of work how much intelligence that unit deserves and proves afterwards where the money went. A five-stage, queue-based pipeline - ingestion, cheap NLP, router, selective LLM and result assembler - emits one schema-validated JSON document per thread. A six-gate router governs post-level spend, while a separate step decides which comments an eight-labeller ensemble reads: seven small multilingual sentiment heads batched on CPU plus one context-aware LLM stance pass, in which a labeller that cannot answer abstains. Watchlist-driven target stance adds per-entity verdicts through an alias matcher built for the three-script spelling problem, and nine tool-using agents reason over the system's own output through eighteen typed Model Context Protocol tools. Over 50 threads carrying 10,272 real comments the router sends 16 percent of posts to post-level work against 74 percent for a keyword baseline, yet governs only 30 percent of spend because 96 percent of calls are per-comment; hybrid retrieval reaches recall@10 of 0.8750 against 0.1875 for hash-vector baselines. The deliverable is working, auditable software in which every capability is reported alongside its class of evidence.

@CHAPTER|1|Introduction

@INTRO|This chapter states the problem the project addresses, the computational reasons that make it worth solving, the objectives that follow from it, and a summary of the method and the outcomes. It closes with a chapter-by-chapter map of the rest of the report.

@H2|1.1  Introduction

@P|Bangladesh has one of the largest and most conversational social-media populations in South Asia, and the organisations that monitor it - newsrooms, brand agencies, election observers, civic groups - increasingly procure that monitoring as a service. A monitoring platform of this kind scrapes public posts and their comment threads, stores them, and exposes them over a REST interface. What it typically does **not** do is understand them. The platform that supplies the data for this project stores one coarse sentiment score per post, leaves per-comment sentiment entirely empty, and ships no optical character recognition for the images attached to a post. Everything an analyst actually wants to know - what the thread is arguing about, which commenters are angry and at whom, whether a conversation is turning toxic, what the dominant themes are this week - has to be computed by something else.

@P|Computing it is harder here than the English-language literature suggests, for one specific reason. The text is not Bangla, and it is not English. It is a live mixture of both, written in two scripts, with no standard orthography for the mixture. A single thread routinely contains comments in Bangla script, comments in English, and comments in **Banglish** - Bangla rendered in Latin characters with spellings that vary from writer to writer and sometimes within a single comment. Measured over the 10,272 comments in this project's working corpus, 81.4 percent of comments contain Bangla script only, 11.1 percent contain Latin script only, 4.6 percent contain both, and 2.9 percent contain neither script at all because they are pure emoji. Multilingual encoders degrade on the romanized portion precisely because it is neither of the languages they were pretrained on, and the same named entity may appear in three different scripts and half a dozen spellings across one thread.

@P|The obvious response - send every post and every comment to a large language model - works and is unaffordable. At the volumes a monitoring platform generates, per-token billing or per-token GPU occupancy scales with the number of comments, not the number of posts, and a single viral thread in this corpus carries 2,857 stored comments against a platform-reported total of 9,224. The opposite response - run only small, cheap classifiers - is affordable and demonstrably weaker on exactly the code-mixed text that dominates the traffic.

@P|The problem statement of this project is therefore narrower and more testable than "analyse Bangla social media". It is this: given a post together with its embedded comment thread, decide *per unit of work* how much intelligence that unit deserves, spend the expensive model only where cheap models cannot answer, and be able to prove afterwards, from the system's own counters, where the money went and what produced every label. The result is a self-contained analysis microservice that pulls from the upstream platform, analyses in its own database, writes nothing back, and returns one structured JSON document per thread for downstream consumers.

@H2|1.2  Motivation

@P|The computational motivation is a cost asymmetry that is large enough to design a system around. A small transformer classifier of 135 to 280 million parameters, batched on CPU, labels a short comment in the order of a hundred milliseconds and costs nothing per token. A seven-billion-parameter instruction-tuned model answers the same question better on code-mixed text, but a single post-type call on the local deployment used in this project takes between 7 and 50 seconds, and one Stage-2 call on a batch of 25 comments is a generation call whose cost scales with prompt length. The gap between the two is between two and three orders of magnitude in latency and, on a metered backend, a comparable gap in money. A system that can decide *which* items genuinely need the expensive path converts an unbounded bill into a bounded one.

@P|That decision is not free to make well, and this is the part that makes the problem interesting rather than merely engineering. A confidence gate is only as good as the confidence estimate feeding it, and a confidence estimate produced by a model that has never been calibrated on the target language is a guess wearing a number. The literature on cascades and query routing - FrugalGPT [30], RouteLLM [31], Hybrid LLM [32] - establishes the shape of the answer for English. What it does not establish is what the gate should read when the input is code-mixed, when a post has no text at all, or when the "unit" being routed is a thread of thousands of comments rather than a single query.

@P|A second motivation is a research gap that this corpus makes visible. Document-level sentiment establishes whether a comment carries negative affect. For political and brand monitoring the operative question is a different one: the identity of the entity toward which that affect is directed. Target-dependent stance detection is well established for English product reviews and English tweets [13], [14], [16], but for code-mixed Bangla it is under-served, and the hard part is not the classifier - it is the matcher, because the same entity is written three ways and a watchlist that matches one spelling silently matches almost nothing. A failure of that kind is invisible: it produces zero mentions, a result indistinguishable from an entity that was never discussed.

@P|A third motivation is personal and professional. Building this system required standing up a genuine distributed pipeline - durable queues, stateless workers, dead-letter handling, autoscaling manifests, three storage engines chosen by access pattern, an observability stack - alongside the applied NLP. That combination is exactly the skill set the industry asks for and exactly the combination an undergraduate curriculum rarely exercises end to end. Solving it also forced a discipline that was not expected to be the most valuable outcome of the project: **every claim in this report is labelled with the class of evidence behind it**, because six independent audit passes over the project's own code established that the most consequential failures were not incorrect answers but silent successes - components that reported that they had run when they had not.

@H2|1.3  Objectives

@P|Four objectives follow from the problem statement of Section 1.1, and each answers one of the four gaps identified in Section 2.3. Each is scoped so that it can be checked against the running system rather than argued for, and they are ordered so that the earlier ones are preconditions for the later ones.

@NUM|O1.  **Build the analysis service.** To design and implement a horizontally scalable, queue-based analysis microservice that consumes a post-with-details payload - a post with its comment thread, engagement counts, reaction breakdown and share sample embedded - from an existing monitoring platform, analyses it in its own datastores, and returns one schema-validated JSON document per thread without ever writing back to the upstream platform.
@NUM|O2.  **Make the cascade selective, and measure it.** To implement a hybrid cascade in which cheap NLP runs on every post and every comment while a rule-based router decides, per post, whether post-level large-language-model work is warranted and, as a separate decision, which comments the expensive labellers read - and then to measure that cascade rather than assert it, reporting the routing rate from the router's own counters, the split of large-model calls between the post-level and comment-level lanes, and the share of total spend the routing gate actually governs.
@NUM|O3.  **Deliver the capability layers the code-mixed setting needs.** To raise per-comment sentiment from a single verdict to a transparent eight-labeller ensemble in which a labeller that cannot answer abstains rather than casting a fabricated neutral vote; to add watchlist-driven target stance through a configurable, alias-aware entity list that yields per-entity verdicts for Bangla, Banglish and English text in a field kept separate from document sentiment; and to build an agentic insight layer in which tool-using agents reason over the system's own output through Model Context Protocol servers, under per-run tool and token budgets, prompt-injection hardening and citation verification.
@NUM|O4.  **Make every claim auditable, and evaluate against that standard.** To carry provenance on every label, per-backend and per-lane cost telemetry, a live per-post execution trace and a regression suite that fails when a repaired defect returns; and to evaluate the system on the properties by which an engineering deliverable is judged - retrieval quality, routing behaviour, call and cost splits, coverage arithmetic and system correctness - attaching an evidence class to every published claim so that the boundary of what was evaluated is part of the result rather than something the reader has to infer.

@P|Aggregated, these four objectives put the project one notch beyond a theoretical problem statement and into actual system fabrication. They were prioritised in the order given: the pipeline and its router first (O1, O2), the capability layers second (O3), and the audit, evaluation and evidence discipline last (O4). That is the order in which Chapter 3 develops them and Chapter 4 measures them, and the gap analysis of Section 2.3 states the four gaps they answer, one for one.

@H2|1.4  Methodology

@P|For this project, an iterative development methodology structured around requirement analysis, design, development, testing, deployment and audit was adopted. The work was carried out in six steps, each with a clear objective, a defined process and a measurable outcome, so that the delivered system does not drift from the objectives stated in Section 1.3. The methodology is summarised below through those six steps and is developed in full in Chapter 3.

@H4|1. Requirement Analysis

@P|The objective was to identify the functional and technical needs of a code-mixed Bangla analysis service, as evidenced by what the upstream monitoring platform does and does not supply.

@BULLET|Reviewed the literature on Bangla and code-mixed sentiment, on cost-aware model cascades, and on retrieval-augmented generation and tool-using agents, to establish which parts of the problem already have published answers.
@BULLET|Characterised the real payload rather than a specification of it: 50 threads, 10,272 stored comments, one coarse upstream sentiment per post and no per-comment sentiment at all.
@BULLET|Performed the gap analysis of Section 2.3 against commercial listening suites, the upstream platform itself, academic Bangla classifiers, general retrieval assistants and published router frameworks.
@BULLET|Grouped the requirements around the high-level entities the system actually handles - posts, comments, jobs, watchlist targets, agent runs and analysis results.

@P|The outcome was the eighteen functional and twelve non-functional requirements of Section 3.1.3, and an input contract locked against the real payload rather than against a description of it.

@H4|2. System Design

@P|The objective was to design a scalable architecture in which cheap analysis runs unconditionally and expensive analysis is spent selectively, and define the modules that realise it.

@BULLET|Architected the system as five queue-decoupled stages - ingestion, cheap NLP, router, selective LLM and result assembler - connected by durable streams, so that each stage scales independently.
@BULLET|Designed the router as **two independent decisions** rather than one: whether a post earns post-level large-model work, and which of its comments the Stage-2 labellers read. Separating them is what later made the cost behaviour measurable at all.
@BULLET|Split storage by access pattern rather than by subject: PostgreSQL with pgvector for operational rows and the embedding index, ClickHouse for analytical events, Redis for streams and counters, object storage for raw payloads.
@BULLET|Specified the canonical output document, its JSON Schema, and the data-flow diagrams of Section 3.1.4, together with the eleven-tab dashboard layout of Section 3.1.5.
@BULLET|Recorded, for every significant decision, the alternatives weighed and the constraint that settled it, in Table {{tab:alternatives}}.

@P|The outcome was the architecture of Figure {{fig:architecture}}, the pipeline of Figure {{fig:pipeline}}, the canonical schema, and a design specification in which no load-bearing choice is undocumented.

@H4|3. Development

@P|The objective was to translate the designed modules into a working system rather than a prototype.

@BULLET|Implemented the five stages, the six-gate router and the two-lane Stage 2, with a shared worker base class carrying consumer-group creation, cooperative cancellation, bounded retry and dead-lettering.
@BULLET|Built the eight-labeller comment ensemble with its abstention protocol - seven small sentiment heads batched on CPU and one context-aware stance pass - behind a single combiner that is the only writer of a comment's final label.
@BULLET|Implemented watchlist-driven target stance, whose load-bearing part is the alias matcher rather than the classifier, and which adds no additional large-model calls because the matched entities ride inside a prompt already being issued.
@BULLET|Built the agentic insight layer: three Model Context Protocol servers exposing eighteen typed tools, and nine tool-using agents over them with per-run tool and token budgets.
@BULLET|Built the operator-facing React dashboard, the 51-path HTTP API beneath it, and the Server-Sent Event streams that carry every live surface.

@P|The outcome was A running system of 56,789 lines of Python across 182 files, a React dashboard, three deployment shapes and an evaluation harness - the software described in Chapter 4.

@H4|4. Testing

@P|The objective was to validate the implemented modules for functional correctness, contract compliance and honesty of reporting.

@BULLET|Wrote contract tests asserting that every document crossing a boundary validates against its schema, and structural tests asserting that the deployment manifests name exactly the streams the workers create.
@BULLET|Ran six independent fresh-eyes audit passes over the system, each pass starting from a claim made in this report and checking it against the running code rather than starting from the code and looking for bugs.
@BULLET|Pinned every repaired defect with a regression test named after the defect, and confirmed by mutation testing that the tests fail when the fix is reverted.
@BULLET|Assembled the whole verification chain - Python suite, dashboard unit tests, lint, production build and browser tests - into one pass-or-fail command.

@P|The outcome was A 1,420-test suite in which test code is 35 percent of the repository, and a full chain that passes in seventy-three seconds. It also produced findings that contradicted the project's own headline claim, which are reported as such in Section 4.3.2.

@H4|5. Deployment

@P|The objective was to make the same codebase runnable on a laptop and in a cluster without a rewrite.

@BULLET|Packaged the system for three tiers: a single-host development stack, a nineteen-image Docker Compose deployment, and a Kubernetes deployment with queue-depth autoscaling.
@BULLET|Made the inference backend pluggable and resolvable per call, so that self-hosted and metered serving are a configuration decision rather than a migration.
@BULLET|Enforced a tenant privacy lock that pins a locked tenant to the self-hosted backend on every path and fails closed when the policy table cannot be read.
@BULLET|Reduced the whole stack to a single start command that brings up four containers and eleven host processes and verifies the sentence encoder before launching anything.

@P|The outcome was A system that starts in under a minute on a laptop and expresses the same components as Kubernetes objects in production, which is what makes it demonstrable rather than merely deployable.

@H4|6. Evaluation and Future Planning

@P|The objective was to measure what the system does, and state plainly where the evidence stops.

@BULLET|Measured system properties - routing rate, call and cost split, coverage, latency, label provenance - by running the real stage functions over the real corpus.
@BULLET|Measured retrieval quality against a 32-query known-item set with recall@k, MRR@k and nDCG@k, and stratified it by query-to-target lexical overlap.
@BULLET|Attached an evidence class to every capability - measured, works-but-unmeasured, unexercised, or out of scope - and recorded it in a single ledger.
@BULLET|Scoped the annotation programme that a labelling-accuracy figure would require, and built its sampler and scorer without seeding it with labels drawn from the system's own models.

@P|The outcome was four completed measurement studies, an evidence ledger covering every capability, and the ordered future work of Section 6.3.

@P|Evaluation is deliberately split by what the evidence can support, and that split is the methodological commitment this project would defend first. System properties are measured. Retrieval quality is measured against ground truth. Correctness is pinned by regression. Labelling accuracy is **outside the evaluation scope** and is not claimed, because obtaining it honestly requires an annotation programme rather than a further measurement script.

@H2|1.5  Project Outcome

@P|The delivered solution is a working, auditable analysis microservice with evidence of implementation across ingestion, the five-stage pipeline, the comment ensemble, the watchlist stance layer, the agentic insight layer and an eleven-tab operator dashboard. It comprises 56,789 lines of Python across 182 files, of which 19,850 lines are tests, together with a React dashboard, deployment manifests for both Docker Compose and Kubernetes, and an evaluation harness. A summary of the key results of this work is given below.

@H4|1. A working cost-aware cascade with measured behaviour

@P|On the 43-post captioned corpus, the router sends 16 percent of posts to post-level large-model work under the shipped Stage-1 engine, against 74 percent under a keyword baseline. More importantly, the measurement showed that the routing rate is *not* the cost story, because 96 percent of calls are comment-level. This is a result that contradicted the project's own original claim and is reported as such in Section 4.3.2.

@H4|2. A transparent per-comment ensemble

@P|Eight labellers per analysed comment, with abstention, voter counts, and per-source verdicts surfaced side by side in the dashboard, so a sentiment chart can always say what produced its numbers. A comment that no model read is reported as *uncertain* rather than defaulted to neutral.

@H4|3. A built and tested watchlist stance capability

@P|Per-entity stance over an operator-supplied, alias-aware watchlist that adds zero additional large-model calls, because the matched entities ride inside a prompt that is already being sent. It is framed in the output schema as a separate measurement from sentiment, and never summed or charted with it.

@H4|4. An agentic insight layer

@P|Nine tool-using agents over eighteen typed tools across three Model Context Protocol servers, with a runner hardened against eight distinct failure modes observed in live runs, each of which now has a regression test.

@H4|5. A measured retrieval stack

@P|Hybrid retrieval reaches recall@10 of 0.8750 where hash-vector baselines score 0.1875 - statistically indistinguishable from returning ten random posts out of fifty. Stratifying the query set shows the dense and lexical arms failing on disjoint query populations, which is the real argument for fusing them.

@H4|6. An operator-facing product, not a script

@P|Eleven dashboard tabs - corpus overview, post explorer, job control, reports, dual-mode search, agents, chat, pipeline, per-post trace, watchlist warnings and a streaming log console - over a documented 51-path API, with host telemetry, light and dark themes, and a one-command start of the whole eleven-process stack. Section 4.3.1 walks through all of it with screenshots of the running system, and Table {{tab:features}} indexes each feature against the figure that shows it.

@H4|7. An honest capability ledger

@P|Every feature is classified as measured, works-but-unmeasured, unexercised, or out of scope. The image modality is reported as unexercised rather than claimed, and labelling accuracy is recorded as a stated scope boundary with the work that would close it named in Chapter 6.

@P|The areas that have not fully matured are reflected in the deliverable rather than hidden by it: the image and optical-character-recognition modality, cluster autoscaling in a real cluster, and the scoring of the agent layer's answers are all on the future-scope pipeline of Section 6.3 rather than in the results.

@P|The potential outcomes beyond the project are a deployable analysis layer for any Bangla-language monitoring platform, a reusable pattern for cost-aware model cascades in low-resource settings, and a corpus of 10,272 real code-mixed comments with crowd reaction signals attached that is ready for the annotation effort that would turn this engineering result into a benchmark result.

@P|The results confirm that this project has moved beyond a written problem statement and into a deployed, inspectable system, with demonstrated coverage of each of the following: ingestion and the five-stage pipeline, the six-gate router and its measured behaviour, the eight-labeller comment ensemble, watchlist-driven target stance, the agentic insight layer over eighteen typed tools, hybrid retrieval with a measured quality figure, and an eleven-tab operator dashboard over a 51-path API. The areas that have not fully matured - the image modality, cluster-scale autoscaling, and the scoring of the agent layer's answers - are named as such in the capability ledger rather than presented as delivered, which is itself one of the seven outcomes above.

@CHAPTER|2|Background

@INTRO|This chapter supplies the background needed to read the rest of the report. It reviews the state of sentiment and stance analysis for Bangla and code-mixed text, the literature on cost-aware model cascades, and the recent work on retrieval-augmented generation and tool-using agents, then compares the proposed system against existing monitoring products and identifies the gaps this project sets out to fill.

@H2|2.1  Introduction

@P|Three separate research literatures meet in this project, and each contributes a different piece of the design. The first is **sentiment and stance analysis for low-resource and code-mixed languages** - a field whose general methods and open problems are surveyed by Wankhade et al. [12], which supplies the models and, more importantly, the evidence about how badly those models degrade when the input is romanized. The second is **cost-aware inference**, a line of work on cascades and query routing that establishes the shape of a system in which a cheap model answers most queries and an expensive model answers the rest. The third is **retrieval-augmented generation and tool-using agents**, which supplies the pattern for the insight layer that sits above the per-post pipeline.

@P|A short orientation on each is given here; the detailed comparison follows in Section 2.2.

@P|Modern text classification for this task rests on the transformer encoder [18] and the masked-language-model pretraining objective introduced by BERT [19]. For multilingual settings, XLM-RoBERTa [20] is the standard baseline: a single encoder pretrained on one hundred languages, which handles Bangla and English in one model and therefore handles a code-mixed sentence without a language-identification step in front of it. For Bangla specifically, **BanglaBERT** [1] is the leading monolingual option, pretrained on a large Bangla corpus and accompanied by the BLP benchmark suite. Both matter here: the ensemble described in Chapter 3 deliberately mixes multilingual encoders with Bangla-specific fine-tunes, because a multilingual model that merely *includes* Bangla is a different kind of evidence from a model trained on it.

@P|Sentence-level embeddings for retrieval and clustering come from the Sentence-BERT family [22], and specifically from its multilingual distillation variant [23], which is what allows an English query to retrieve a Bangla post. Named-entity recognition uses GLiNER [25], a generalist recogniser that accepts arbitrary entity types at inference time rather than requiring one model per type; language identification uses fastText [21]; and topic and intent assignment where no labelled data exists uses the label-embedding and entailment-based zero-shot formulations surveyed by Yin et al. [26]. ModernBERT [24] is included in the ensemble as a recent long-context encoder with a different pretraining recipe from the rest of the roster, on the grounds that a voter that fails differently is worth more than a voter that fails the same way.

@P|Code-switching is not an edge case in this corpus; it is the dominant register. One further property of this register is recorded here because it shapes an annotation decision in Chapter 6: a large share of comments carry emoji, whose sentiment is neither uniform nor obvious and has been measured directly across languages by Kralj Novak et al. [17]. Sitaram et al. [11] survey the code-switching field and note the central practical difficulty: romanized text belongs to no language model's pretraining distribution, and standard tokenisers fragment it badly. SemEval-2020 Task 9 [10] established shared benchmarks for Hindi-English and Spanish-English code-mixed sentiment and confirmed that performance on the code-mixed portion lags the monolingual portion substantially. For Bangla specifically, Hassan et al. [3] were among the first to treat romanized Bangla as a first-class target rather than as noise, and Sazzed [4] showed the same for transliterated abusive content. Alam et al. [9] survey the whole Bangla NLP landscape and reach a conclusion that shaped this project's evaluation plan: the bottleneck is annotated data, not model architecture.

@P|The engineering core of this project belongs to a line of work that is only a few years old. FrugalGPT [30] showed that a cascade of increasingly capable models, gated by a learned scorer, can match a single large model's quality at a fraction of the cost. RouteLLM [31] learned the routing decision from preference data, and Hybrid LLM [32] framed it explicitly as a cost-versus-quality trade with a tunable knob. All three route **queries**. None of them routes a *thread*, and the distinction turns out to matter a great deal: as Chapter 4 shows, when the unit of analysis contains thousands of sub-items, the routing decision on the container governs a minority of the eventual bill. On the serving side, PagedAttention and vLLM [33] are what make self-hosted inference economical enough for the local backend to be the default.

@P|Retrieval-augmented generation [34] grounds a generated answer in retrieved evidence; the survey by Gao et al. [35] maps the design space that has grown around it. Retrieval quality is the binding constraint, and the standard measures are recall@k, MRR@k, and the cumulated-gain measures of Järvelin and Kekäläinen [41]. Where dense and lexical retrieval each fail on different queries, reciprocal rank fusion [39] is the standard way to combine them without having to make two incomparable score scales agree; approximate nearest-neighbour search over the dense arm uses HNSW graphs [40]. Cuconasu et al. [42] give an important warning that shaped this project's decision to report recall rather than precision: what lands in the retrieved context materially changes the generated answer, so the metric that matters when the whole top-k is handed to a model is recall at k. Beyond single-shot retrieval, ReAct [36] and Toolformer [37] established the tool-using loop, and the Model Context Protocol [38] standardises the tool interface itself - along with, as Hou et al. document, a new attack surface.

@H2|2.2  Literature Review

@P|Related work is reviewed across the three research areas that bear directly on this design: sentiment and stance analysis for Bangla and code-mixed text, cost-aware model cascades and query routing, and retrieval-augmented generation with tool-using agents. Table {{tab:litreview}} carries the detailed comparison - author, year, methodology, and the finding that shaped this project - for the twelve works that most directly informed the design, ordered so that the three areas remain visible in the table. The paragraphs below state only what the table cannot: why each group of works matters here. The wider body of work these rest on - transformer encoders, multilingual sentence embeddings, serving techniques, rank fusion, evaluation protocols and the prompt-injection threat taxonomy - is introduced in Section 2.1 and cited at the point of use in Chapters 3 and 5.

@P|**Bangla and code-mixed language processing** [1], [2], [4], [5], [6], [9], [10] supplies this project's models and its scope boundaries. BanglaBERT [1] is the strongest monolingual Bangla encoder available and contributes two of the seven cheap sentiment heads, so Bangla is judged by models trained *on* Bangla rather than only by multilingual models that happen to include it; the SentNoB fine-tune [2] contributes a third, and its finding that noisy social text is materially harder than curated Bangla is why a benchmark score on clean Bangla is never treated here as evidence about comment threads. Sazzed [4] and Nezami and Huda [6] are the closest published formulations to this project's actual input register, and both establish that transliteration rather than vocabulary is the primary source of error - which is why romanized Banglish is a separate reporting bucket throughout this report rather than being folded into Bangla. Romim et al. [5] inform the toxicity gate and its threshold. Two conclusions from this group are load-bearing for the evaluation plan: Alam et al. [9] find that annotated data, not model architecture, is the binding constraint for Bangla, which is why this project spends its effort on the system and on label provenance and scopes the annotation programme as future work; and Patwa et al. [10] supply the evaluation protocol that programme would adopt, together with the size of the code-mixed-to-monolingual gap it would be measuring.

@P|**Stance detection and cost-aware inference** [13], [30], [31] supply the two mechanisms the system is built around. Kucuk and Can [13] define the task the watchlist feature implements and establish two things this design depends on: that stance toward a target and document sentiment are distinct quantities - which is why they occupy separate output fields here and are never summed or charted together - and that the target-dependent formulation is under-served outside English, with benchmarks that assume a small fixed target set rather than an operator-supplied one. FrugalGPT [30] is the foundational cost-cascade result and the direct ancestor of this project's router; this project implements the same idea with a rule-based rather than a learned gate, and contributes back a measurement of where the analogy breaks when the routed unit is a thread rather than a query. RouteLLM [31] shows the routing decision can be learned instead of hand-tuned, and is identified in Section 6.3 as the single most valuable upgrade to the gate - sequenced after the annotation programme, because a learned router needs labels to learn against.

@P|**Retrieval-augmented generation and tool-using agents** [34], [35], [38] supply the insight layer. Lewis et al. [34] and the survey by Gao et al. [35] establish the pattern of grounding a generated answer in retrieved evidence; this project generalises it in one specific respect, in that its agents retrieve the system's **own structured analytical output** rather than documents a user could have read anyway, which makes the retrieval analytical rather than documentary and allows a cited number to be traced back to the model that produced it. Hou et al. [38] describe the tool-interface standard adopted here together with its attack surface, and their threat analysis - read alongside the indirect-prompt-injection taxonomy of Greshake et al. [43] - is what motivated the runner hardening of Section 3.2.6.

@P|Table {{tab:similar}} carries the comparison in full. Three points from it are worth stating in prose. First, the closest system to this one is the **upstream platform itself**: it scrapes reliably and keys records by stable identifiers, but leaves comment sentiment null on every one of the 10,272 comments in the sample, ships no optical character recognition and computes no embeddings - it is a data source, not an analysis layer, which is the precise gap this microservice fills. Second, **commercial listening suites and academic Bangla classifiers fail in opposite directions**: the suites are complete products that are closed and shallow on Bangla, so an operator cannot see, swap or audit the model behind a label, while the academic systems produce good models and no system at all - no ingestion, no routing, no cost model and no serving path. This project consumes several of the latter at once inside a deployable layer that reports which of them actually spoke on each comment. Third, **general RAG assistants and router frameworks are components rather than systems**: the assistants retrieve text a user could have read anyway and have no defence against instructions embedded in retrieved third-party content, and the router frameworks carry no ingestion contract and no cost telemetry with which to check afterwards whether routing saved anything - which is exactly why this project's measured finding in Section 4.2.4 was visible here and is absent there.

@P|each reviewed class offers a solid, focused solution to one discrete part of the problem, and none consolidates them into a single cost-aware, auditable analysis layer for code-mixed Bangla in which every label can say what produced it. That persistent fragmentation is the first of the four gaps stated below.

@H2|2.4  Summary

@P|The background divides cleanly. From Bangla and code-mixed NLP this project takes its models and, more usefully, the established finding that romanized text is where those models fail and that annotated data is the field's binding constraint. From the cost-aware inference literature it takes the cascade pattern, and it contributes back the observation that the pattern's cost accounting changes when the routed unit contains thousands of sub-items. From retrieval and agent research it takes the tool-using loop, rank fusion and the recall-oriented evaluation protocol, and it contributes an analytical rather than documentary retrieval target together with the guards a deployment on adversarial content requires. The four gaps in Section 2.3 are the specification for Chapter 3, and each is answered by the objective of Section 1.3 that carries the same number.

@CHAPTER|3|Research Methodology

@INTRO|This chapter specifies the system. It states the requirements the design has to meet, presents the architecture and the five-stage pipeline that realises it, develops each of the load-bearing components in detail, records the alternatives that were considered at every significant decision point and why the chosen option won, and closes with the project plan and the allocation of work.

@H2|3.1  Requirement Analysis and Design Specification

@H3|3.1.1  Overview

@P|The system is a **self-contained analysis microservice** that sits beside an existing social-media monitoring platform. Its contract with that platform is deliberately one-directional: it **pulls** a post-with-details payload, analyses it in **its own** datastores, and **never writes back**. The payload is one JSON object per post carrying the post itself, its embedded comment thread, an engagement block, a reaction breakdown and a sample of shares. Because the comments arrive embedded, no second fetch and no join are required, and the natural unit of analysis is not a post but **a post together with its comment thread**.

@FIGURE|fig:integration|Integration model: a read-only pull into a separate datastore.
@FIGHEIGHT|58
@FIGNOTE|In Figure {{fig:integration}}, the integration contract is shown as four elements on one vertical path: the upstream monitoring platform this project does not own, Selective Intelligence itself, this project's own storage tier (PostgreSQL with pgvector, ClickHouse, Redis and object storage), and the operator surface. The descending arrow is a single pull of one whole payload - the post together with its comments, engagement, reactions and shares - and it corresponds to Process 1.0 (Ingest) of the data flow diagram shown in Figure {{fig:dfd1}}, entering on flow [1] and written unchanged into D1 (posts and raw payloads) as indicated by flow [3]. The dotted arrow climbing back to the platform is the one edge describing something the system does not do, and it has no counterpart in the level-1 diagram at all: records are keyed by the upstream identifier, so a repeated pull is an upsert rather than a duplication, and no analysis is ever written back.
@ENDFIGURE

@P|Everything downstream follows from three properties of that input. First, the thread is a **sample**, not a census: the payload reports how many comments the platform holds and how many it actually shipped, and in this corpus the second number is 3.75 percent of the first. Any honest output has to report that coverage rather than imply completeness. Second, the platform supplies **one coarse sentiment score per post and nothing at all per comment**, so per-comment sentiment is entirely the responsibility of this service, and the upstream score is retained only as a baseline for comparison. Third, the text is **code-mixed**, which means model selection cannot be a single choice.

@P|Figure {{fig:integration}} states the position this system occupies relative to the platform that feeds it, and three properties follow from it. The first is that the payload arrives **whole**. A post, its comment thread, its engagement counts, its reaction breakdown and a sample of shares come in one pull, so the system never issues a comment fetch per thread and never has to reason about a partially retrieved thread. This is the precondition for thread-level analysis: the unit of work is a complete conversation, and it is complete on arrival.

@P|The second is that records are keyed by the **upstream identifier**. Pulling the same post twice is therefore an upsert rather than a duplication, which makes the ingestion path idempotent without any coordination between the two systems, and makes a re-pull a safe recovery action rather than a corruption risk.

@P|The third is the dotted arrow, which is the only edge in the figure describing something that does not happen. Nothing is ever written back to the upstream platform. This is a deliberate architectural commitment rather than an unimplemented feature: it means the system cannot corrupt the source of truth, that it can be removed entirely without leaving residue in the platform, and that its analytical output is free to be wrong in ways that would be unacceptable if it were mutating a shared record. It is also what makes the separate datastore in the middle of the figure necessary rather than redundant - having declined to write to the upstream database, the system must own one.

@P|The design responds with a five-stage, queue-decoupled pipeline in which cheap analysis runs unconditionally and expensive analysis is spent selectively, plus two layers that sit outside the per-post path: a watchlist stance capability carried inside a prompt that is already being issued, and a corpus-tier agentic layer that is never invoked per post. Figure {{fig:architecture}} gives the high-level architecture and Figure {{fig:pipeline}} the pipeline.

@H3|3.1.2  System Design

@FIGURE|fig:architecture|High-level architecture of the Selective Intelligence microservice.
@FIGHEIGHT|92
@FIGNOTE|In Figure {{fig:architecture}}, the whole deployed system is shown as five bands: the clients (the web dashboard and any third-party consumer, both entering over HTTPS through the gateway), the FastAPI tier split into authentication, ingestion and reporting, the per-post pipeline of Stage 1, router, Stage 2 and assembler, the agentic insight layer reached from the reporting service, and the storage tier of four cylinders. The pipeline band realises Processes 1.0 (Ingest) to 5.0 (Assemble) of the data flow diagram shown in Figure {{fig:dfd1}}, the insight layer realises Process 6.0 (Insight), and the storage band holds D1 (posts and raw payloads) through D5 (analytics events and comment sentiments). @ENDFIGURE

@P|The figure is organised as five horizontal bands, and each boundary between them is a place where the system deliberately gives something up in exchange for a property it needs. The **client band** contains two consumers that are treated identically: the project's own dashboard and any third-party application. Neither is privileged, because both arrive through the same gateway over the same authenticated HTTP surface; the dashboard holds no private channel into the system, which is what makes the API the product rather than the user interface.

@P|The **gateway** terminates TLS, routes, and applies rate limits. Placing it ahead of the service band means that the services behind it never implement transport security or quota logic, and that the production tier can substitute a Kubernetes ingress for NGINX without any service being aware of the change.

@P|The **service band** splits into authentication, ingestion and reporting. That split is by *lifetime of the request*, not by subject matter. Authentication answers in milliseconds and holds no domain state. Ingestion validates a payload, deduplicates it against a content hash and returns as soon as the work is durably enqueued, so the caller is never held open for the length of an analysis. Reporting serves reads and generates documents, and it is the only service that may take seconds to answer. Collapsing any two of these into one process would couple response-time budgets that have no reason to be coupled, which is precisely the simplification the MVP tier accepts and the production tier reverses.

@P|Only ingestion writes to the **message bus**, and this is the single most consequential arrow in the figure. It means the pipeline has exactly one entry point, so every post in the system arrived the same way and carries the same envelope. It also means the write path and the read path share no component: a pipeline stalled behind a slow model does not slow a report, because reporting reads from storage and never from the bus. The bus itself is drawn as one box with two implementations because the pipeline's contract with it is narrow - durable append, consumer groups, partitioning by a hash of the post identifier - and both Redis Streams and Kafka satisfy it.

@P|The **pipeline band** is the subject of Section 3.2 and of Figure {{fig:pipeline}}. What matters at this level is only that the router sits inside it, between the two analysis stages, and that it is the sole component in the entire figure permitted to decide how much work an item receives. No other box makes that judgement, which is why cost behaviour can be reasoned about by reading one component rather than by auditing the whole system.

@P|The **agentic layer** is drawn to the side rather than in the chain, and its only inbound edge comes from reporting. That placement encodes the cost boundary that Section 3.2.6 develops: agents run per question, at corpus scale, and are never invoked per post. Had the layer been drawn inside the pipeline band it would have inherited the per-post invocation rate, and the generation cost the cascade exists to avoid would have re-entered the system through the analytical layer.

@P|The **storage band** is split by access pattern rather than by subject. Four stores receive the assembler's fan-out; only two of them are ever read back. PostgreSQL with pgvector holds operational rows, job state and the embedding index, and is the store the reporting service and the tool servers query. ClickHouse holds append-only analytical events. Redis holds cache entries, the deduplication set and counters. Object storage holds raw payloads and generated reports. Because ClickHouse is written from the same canonical result that PostgreSQL receives, it is derivable rather than authoritative: it can be dropped and rebuilt from the raw payloads without an operational read ever noticing, which is a property that a single general-purpose database would not have offered.

@P|Four principles govern the design, and each of them is visible somewhere in Figure {{fig:architecture}}.

@NUM|P1. **Hybrid intelligence, not a large model everywhere.** Small specialised models are two to three orders of magnitude cheaper and faster per item. The large model is a scalpel, reserved for what small models cannot do at all - writing prose, or for the cases where a small model is genuinely uncertain.
@NUM|P2. **Queue-based and stage-decoupled.** Every heavy stage is a stateless worker pool fed by a durable stream, so back-pressure, retries and independent scaling come for free and no stage's failure can take another one down.
@NUM|P3. **Scale by partition, not by bigger machines.** Throughput grows by adding workers and partitions. The bus is partitioned by a hash of the post identifier, so a given post's ordering is stable while load spreads evenly.
@NUM|P4. **Idempotent and observable.** Every post has a stable content hash, so reprocessing is safe; every stage emits progress events, metrics and traces; and every value in the output carries provenance saying what produced it.

@FIGURE|fig:pipeline|The five-stage per-post pipeline and the single envelope that threads through it.
@FIGHEIGHT|78
@FIGNOTE|In Figure {{fig:pipeline}}, the per-post pipeline is shown as a single chain of five stages - ingestion, Stage 1, router, Stage 2 and assembler - each captioned with the consumer group that runs it, and each arrow labelled with the literal name of the Redis stream that carries work to the next. These are Processes 1.0 (Ingest) to 5.0 (Assemble) of the data flow diagram shown in Figure {{fig:dfd1}} in order, carrying the normalised envelope on flow [4], the stage-1 result on flow [6], the task flags and selected comments on flow [7] and the stage-2 result on flow [10]; the three cylinders beneath the panel are D1 (posts and raw payloads), D2 (analysis_results and embeddings) and D5 (analytics events and comment sentiments), written by flows [11], [12] and [13]. The orange callout hanging off the router is a note rather than a stage, and it contradicts a specific misreading: the chain carries no bypass edge, so the gate governs the quantity of work an item receives and never its route.
@ENDFIGURE

@P|Figure {{fig:pipeline}} names the four streams and the five consumer groups explicitly, because those names are the system's real interfaces. A stage knows nothing about the stage before it except the name of the stream it reads and the shape of the envelope it will find there. Each hop is a durable append rather than a call, so a stage that dies mid-batch loses no work: the entries it had claimed but not acknowledged return to the group and are redelivered. Each stage also runs as its own consumer group, which is what allows the stage-2 worker pool to be scaled to four processes while the router runs as one, without any coordination between them.

@P|One envelope threads the whole chain. Ingestion normalises the upstream payload into it, and every subsequent stage adds fields rather than replacing the document, so by the time the assembler receives it the envelope carries the stage-1 features, the router's flags, the stage-2 outputs and the provenance of each. This is why the assembler can validate the result against a schema in one place: it is the only stage that sees the finished object, and every field in that object arrived with a record of which component produced it.

@P|The most important structural fact about Figure {{fig:pipeline}}, and the one most often misdescribed in the project's own early documentation, is that **the chain is linear**. The router does not divert a post away from Stage 2. It writes every post to the Stage-2 stream and marks the envelope with a flag saying whether post-level work was earned. A post that fails the gate still has its comments analysed, because the entire comment ensemble lives in Stage 2. An earlier design did divert bypassed posts straight to the assembler, and the consequence was that the majority of posts arrived with three empty columns in the per-comment comparison and nothing in the output explaining why.

@H3|3.1.3  Functional and Nonfunctional Requirements

@P|These are requirements on the **project's software system**, not on the research. Functional requirements say what the system must *do*; non-functional requirements say *how well* it must do it. Each is stated once, with the design element that satisfies it named alongside, so that a reviewer can check the mechanism in the code rather than take the requirement on trust.

@P|The system shall pull a post-with-details payload from the upstream platform and accept a pushed batch for replay (FR1), derive the source platform from each post's URL host (FR2), and preserve the upstream coarse sentiment and virality score as baselines it never overwrites (FR3). Over every ingested thread it shall detect language and flag romanized Banglish, reporting the method that produced the verdict (FR4); recompute post-level sentiment, emotion, topics, intents, semantic post type, toxicity, named entities and keywords (FR5); and label every comment in the stored thread with the provenance of that label attached (FR6). It shall decide per post whether post-level large-model work is warranted, through explicit and tunable rules (FR7), and decide separately - through eligibility, deduplication and an optional cap - which comments the expensive labellers read (FR8). Each analysed comment shall receive multiple independent verdicts combined by a single writer, with abstention rather than a default vote (FR9); each post shall receive a summary in its own language that recovers from truncation rather than caching a half-summary (FR10); and per-entity stance toward an operator-supplied watchlist shall be reported in a field separate from document sentiment (FR11). The system shall emit one schema-validated JSON document per thread into three stores (FR12), report comment coverage honestly and clamped with an explicit anomaly flag (FR13), and allow an analysis job to be started, tracked live, stopped, resumed and deleted (FR14). Above the pipeline it shall support identifier, keyword, semantic and hybrid retrieval over analysed posts and comments (FR15) and answer corpus-level analyst questions with grounded, cited answers from tool-using agents (FR16). Finally it shall report token and cost usage per backend, per model and per spending lane (FR17), and expose all of the above through an operator dashboard covering results, jobs, search, agents, chat, pipeline state, per-post trace, watchlist warnings and logs (FR18).

@P|Batches shall scale from one thousand to one hundred thousand threads by adding workers and partitions rather than larger machines, through stateless workers, one durable stream per hop, partitioning by post-identifier hash and queue-depth autoscaling (NFR1); the expensive model shall be spent selectively and the spend shall be attributable afterwards, through confidence-gated routing, comment selection, duplicate and response caching and five-lane usage counters (NFR2); and Bangla, English and romanized Banglish shall all be handled, through a multilingual encoder family mixed with Bangla-specific fine-tunes and per-language reporting throughout the evaluation (NFR3). No post may be silently lost: bounded retry carries its attempt counter inside the payload before dead-lettering with error context, and a dead-lettered post still counts against its job so a progress bar cannot stall forever (NFR4); reprocessing shall be safe, through content-hash keys, upserts on post identifier and a collapsing analytics table (NFR5); and a stop shall cost at most one post per stage, through cooperative cancellation checked at the head of every stage (NFR6). Every stage boundary shall be visible per post through replayed progress events, per-stage timings, metrics, structured logs and traces (NFR7), and no output may claim more than the system did - engine and degraded-component reporting, per-label provenance, a stub-vector flag on every stored embedding and a recorded backend and model on every result (NFR8). Post text shall be treated as untrusted input, with token verification on every transport, API keys stored as hashes, single-use streaming tickets, fail-closed policy checks and untrusted-data delimiters around everything a model is shown (NFR9); a privacy-locked tenant's content shall never leave the cluster, with the backend decision resolved at the API boundary, stamped into the job envelope and re-resolved on resume (NFR10). The same code shall run on a laptop and in a cluster, through Docker Compose, Kubernetes manifests and a stub mode in which every model degrades to a deterministic function (NFR11); and a cross-component rename shall break a test rather than a feature, through single-source constant modules whose agreement with the deployment manifests is test-asserted (NFR12).

@P|The two classes carry different evidence. Every functional requirement above is exercised by the full-chain run reported in Section 4.2.2. The non-functional requirements are not all in that position: NFR1 and NFR6 are properties of a deployment shape that Chapter 4 did not measure, since every measurement was taken on a single host, and Section 4.3.3 records them as claims about the design rather than about observed behaviour.

@H3|3.1.4  Data Flow Diagram

@P|Figure {{fig:dfd0}} gives the context diagram and Figure {{fig:dfd1}} decomposes it one level, to the granularity of six processes and five datastores. The two figures answer different questions. The context diagram fixes the system's boundary: what counts as inside, what counts as outside, and exactly which data crosses between them. The level-1 diagram opens that boundary and shows where state is held.

@P|Four external entities appear at level 0, and the choice of which four is itself a design statement. The upstream platform is a source and never a destination. The operator is both, supplying analysis requests, agent questions and watchlist configuration, and receiving structured results, briefings and reports. The downstream consumer is a destination only. The inference backend is drawn as an external entity rather than as an internal component precisely because it may not be internal: under the metered configuration described in Section 3.2.5, prompts leave the operator's infrastructure entirely, and a diagram that hid the backend inside the system boundary would have concealed the data-residency question rather than posed it.

@P|At level 1 the numbering carries meaning. Processes 1.0 to 5.0 are the per-post tier and execute once per ingested thread; Process 6.0 is the corpus tier and executes once per operator question. The five datastores are separated by who writes them and when. D1 holds posts and raw payloads and is written twice, once on arrival and once after assembly, which is what allows a reanalysis to be replayed from the original payload rather than from a partially processed record. D2 holds the analysis results together with their embeddings, and is the store that retrieval reads. D3 is an exchange rather than a one-way flow, because Process 4.0 both reads and writes it: it is the response cache and the usage counters, and that bidirectionality is the mechanism that makes a repeated analysis cost nothing. D4 is read-only from the pipeline's perspective, holding the model registry and configuration that Process 2.0 consults. D5 holds analytics events and per-comment sentiments.

@P|The most informative feature of the level-1 diagram is what does *not* connect to Process 6.0. No process feeds it directly; it is reachable only through stores D2 and D5. The insight layer therefore reasons over persisted analytical output and never over a post in flight, which is what makes it safe to invoke at a different rate from the pipeline, and what guarantees that an agent's answer is grounded in results that have already been assembled and schema-validated.

@P|Two properties of the component tree are worth reading off Figure {{fig:ui-components}} directly. @P|Figure {{fig:sse}} is drawn separately from the component tree because the two fail in different ways and at different times. A fault in the component tree is a rendering fault, visible immediately and confined to one tab; a fault in the streaming topology is a connection fault, which presents as a surface that simply stops updating while continuing to display its last value - a considerably more dangerous failure for a monitoring product, because stale data and live data look identical. The ticket mechanism shown entering the endpoint panel exists because of a protocol constraint rather than a design preference: an event-source connection cannot carry an authorisation header, so authentication has to move into the query string, and a credential in a query string would be logged by every intermediary. A single-use ticket with a short lifetime is the standard resolution, and it is drawn as entering the panel as a whole because it authenticates all five endpoints identically. The one endpoint feeding two surfaces is the per-analysis stream: job progress and the trace view are two renderings of the same event sequence, so they share one connection rather than opening two.

@H2|3.2  Detailed Methodology and Design

@P|Section 3.1 covered the high-level system design, the requirements, the data flow and the interface layout. This section goes deeper, into the specific technical decisions made in developing the system. For every major architectural decision the alternatives considered are described alongside the justification that led to the final choice. That comparative treatment mirrors what standard engineering practice requires: a component is not adopted because it is the only option in view, but because it scores best against selection criteria - feasibility, cost, scalability, failure behaviour and maintainability - under this project's constraints. Table {{tab:alternatives}} at the end of this section collects thirteen such decisions in one place, and the closing subsection draws out the pattern that runs through them.

@H3|3.2.1  The five stages

@P|Table {{tab:stages}} states the stage topology precisely. Every stream and consumer-group name in it comes from a single constant module, which exists because four separate defects in this system had the identical shape: one component wrote a string, another read a different string, and the mismatch degraded to a silent no-operation rather than to an error. A test now asserts that the Kubernetes autoscaler manifests name exactly the streams and groups the workers create, so a rename breaks the build instead of quietly disabling an autoscaler.

@TABLE|tab:stages|Pipeline stages, streams and consumer groups.
@TH|#|Stage|Reads stream|Consumer group|Writes to|Principal responsibility
@TR|1|Ingestion|ingestion:queue|ingestion-workers|nlp:stage1:queue|Validate against the input schema, normalise Unicode and script tags, compute the content hash, deduplicate, create the job row, enqueue one message per post
@TR|2|Stage-1 NLP|nlp:stage1:queue|stage1-nlp-group|router:queue|Cheap analysis of the caption and of every comment; sentence embedding; watchlist string matching; sentiment fusion; a first summary
@TR|3|Router|router:queue|router-workers|llm:stage2:queue|Evaluate the six gates; set the post-level task flags; select the comment set every Stage-2 voter will read
@TR|4|Stage-2 LLM|llm:stage2:queue|stage2-llm-workers|assembler:queue|Two concurrent lanes: the gated post-level lane and the ungated comment ensemble
@TR|5|Assembler|assembler:queue|assembler-group|PostgreSQL, ClickHouse, object storage|Merge both stages, validate against the output schema, fan out to three stores in parallel, reconcile job counters
@ENDTABLE

@P|Four behaviours are implemented once in a shared worker base class and therefore hold at every hop. **Consumer groups are created on start**, tolerating the already-exists condition, so replicas of a stage split the stream rather than duplicating it. **Cancellation is cooperative**: the four stages ahead of the assembler check a per-job Redis flag as they pick a message up and drop it rather than doing the work, which bounds the cost of a stop at one post per stage. The assembler deliberately does not check, because a post that has reached it has already had every model run on it and discarding it there would throw away work already paid for; what the assembler does instead is refuse to write a cancelled job's row back to a running or done status. **Retry is bounded and then dead-letters**, with the attempt counter carried inside the payload rather than keyed by stream identifier, because a re-enqueued message receives a fresh identifier and a per-identifier counter would reset and loop forever. **Progress events** are published as each stage picks a post up and hands it on; because publish-subscribe has no backlog and the first event is emitted during the request that creates the job, every event is also appended to a capped list and replayed when a client connects, each event carrying a monotonic sequence number so a duplicate can be dropped.

@H3|3.2.2  The router: two independent decisions

@P|The router is the component the entire cost argument rests on, and it makes **two independent decisions**. The first is whether the post earns post-level large-model work; the second is which comments the Stage-2 labellers will read. Conflating them was the original design's mistake, and separating them is what makes the cost behaviour measurable.

@P|The first decision is taken by six gates, listed in Table {{tab:gates}}. Any one gate firing is sufficient to route, and every reason is recorded as a human-readable string on the decision so the routing rate can be decomposed by cause rather than merely counted.

@TABLE|tab:gates|The six routing gates.
@TH|#|Gate|Fires when|Threshold knob (default)
@TR|1|Low or absent confidence|Stage-1 overall confidence is below the threshold, or is absent entirely|ROUTER_CONFIDENCE_THRESHOLD (0.8)
@TR|2|Post type unknown or weak|The semantic post type is unset, or its confidence is below the threshold|ROUTER_POST_TYPE_CONFIDENCE_THRESHOLD (0.8)
@TR|3|Caller asked for a Stage-2 summary|The request explicitly asks for the better summary model|ROUTER_SUMMARY_ROUTES (false)
@TR|4|Image post with no image verdict|The post carries photographs but the vision stage produced no sentiment|not applicable
@TR|5|High toxicity|The Stage-1 toxicity score exceeds the threshold|ROUTER_TOXICITY_THRESHOLD (0.7)
@TR|6|Long code-mixed text|The caption exceeds the character limit and the script is Banglish or mixed|ROUTER_LONG_TEXT_CHARS (1000)
@ENDTABLE

@P|Two decisions inside that table deserve to be stated outright, because both were learned the hard way.

@P|An absent confidence routes. Gate 1 treats a missing value as uncertainty rather than ignoring it. That is not a stylistic choice: in an earlier revision the gate read a field name that Stage 1 never emitted, the guard therefore short-circuited on every post, and a post carrying a confidence of exactly zero passed a threshold of 0.65. The gate was inert and the system routed one hundred percent of posts while every document in the project claimed a single-digit routing rate. The repair was not only to correct the field name but to make **every gate read through a named reader function** that accepts all three field shapes the pipeline emits, and to make the diagnostic log go through those same readers, so a log line can never report a value the gate did not actually see. A rename now fails a test.

@P|Gate 3 is disabled by default, and that default is what makes the gate selective. It once defaulted to enabled, which, because any single gate firing is sufficient, made the router a pass-through and pinned the reported large-model share at exactly one. The product requirement it served, that every post receives a summary, is still met, but by Stage 1, which writes one and hands it to the assembler; Stage 2 re-summarises only when a caller explicitly asks for the stronger model.

@P|The second decision - comment selection - runs in three steps shown on the right of Figure {{fig:router}}. **Eligibility** removes kinds that have no text for a model to read: emoji-only comments, link-only comments, and anything below a configurable word-token floor. **Deduplication** sorts the remainder by reaction count, breaking ties by original index so the choice is reproducible, and collapses identical normalised texts to their most-liked occurrence; on threads in which the same short congratulatory phrase recurs dozens of times, this yields a substantial reduction in cost at no loss of coverage. **Top-N** keeps that many survivors. The cap defaults to zero, admitting every unique comment with text, and the selection is recorded per comment and summarised per post regardless.

@P|Crucially, the selection is made **once**, and every Stage-2 voter reads that same set. An earlier design placed the cap inside the language-model stance pass alone, which recovered the token cost but still ran seven classifier models over the entire thread, and left the language-model column of the per-comment comparison empty on precisely the comments every cheap head had voted on.

@H3|3.2.3  The eight-labeller comment ensemble

@P|Comment sentiment in this system is not a model; it is an ensemble with an explicit abstention protocol. Every comment in the router's selected set collects up to **eight independent verdicts**: seven small sentiment heads batched on CPU, and one context-aware stance pass on the large model - the only labeller that sees the parent post and therefore the only one judging stance *toward* it rather than the comment's own tone. Table {{tab:roster}} gives the roster.

@P|Formally, let *L* be the set of eight labellers and *V(c)* the subset of them that returned a verdict for comment *c*, so that a labeller which cannot answer is absent from *V(c)* rather than present in it with a neutral vote. The combined polarity score and the agreement fraction reported on every comment are then given by Equations ({{eq:ensemble}}) and ({{eq:agreement}}).

@EQ|eq:ensemble|s(@c)  =  ( 1 / n_{c} ) · Σ w_{i} · v_{i}(@c)
@WHERE|The sum runs over the n_{c} labellers in V(@c) that returned a verdict. v_{i}(@c) ∈ {−1, 0, +1} is labeller @i's polarity for comment @c and w_{i} is its weight, with the weights normalised so that s(@c) stays in [−1, +1] however many labellers abstained.
@ENDEQ

@EQ|eq:agreement|a(@c)  =  m_{c} / n_{c}
@WHERE|where m_{c} is the number of those n_{c} labellers that voted for the modal label - the largest bloc among positive, negative and neutral. Equation ({{eq:agreement}}) is the "5 of 8" figure carried on every comment in Figure {{fig:shot-ensemble}}.
@ENDEQ

@P|The two equations share a denominator, and that is the whole point of the abstention protocol: both are normalised by the number of labellers that actually spoke, so a comment read by two labellers cannot present the same confidence as one read by eight. When no labeller answers at all, the combiner emits *uncertain* rather than evaluating either expression.

@P|Four design decisions embodied in that table require justification.

@P|Only a model may label a comment. Stage 1 also produces a cheap emoji-and-lexicon verdict for every comment, and it was originally a ninth voter. It was removed, because it answers on *every* comment, and measurement showed that 71.3 percent of those answers were either the emoji rule or the deterministic stub, which derives a label from a hash of the text and is reproducible without being sentiment. A voter that can never abstain makes every agreement figure unfalsifiable, and on Bangla threads that rule was frequently the *majority* voter. Its verdict is still disclosed in the per-comment provenance field; it is never counted as evidence.

@P|A voter that cannot vote abstains. A head that fails to load, or that returns a label outside the taxonomy, contributes nothing - never a fabricated neutral. The output records how many sources actually spoke, who they were, and which of them stood behind the winning label. A comment that no model read is reported as **uncertain**, not neutral: neutral is a claim about the comment, whereas uncertain is a claim about the system's confidence. Without this distinction, an agreement figure of 1.0 rendered in the interface as "100 percent agreement" for a comment exactly one model had read. A declared-but-silent head is logged at warning level, because five of the roster's original entries were in fact base encoders or were absent from the model hub and had voted zero times while reading as coverage.

@P|Seven heads are not seven independent readings. Five of the seven are multilingual encoders trained on overlapping data, so their agreement is correlated and a seven-to-zero vote is weaker evidence than seven unrelated models would be [50]. This is stated here because it must be stated wherever the agreement number is quoted.

@P|**One combiner is the single writer** of a comment's final label. Three separate places used to write that field and the last one won, which is how a post could report eight negative comments while every comment in the list rendered as neutral.

@H3|3.2.4  Watchlist-driven target stance

@P|Document-level sentiment answers whether a comment is angry. For political and brand monitoring the operative question is **whom it is angry at**, and answering it requires a target-dependent formulation [13], [14], [16]. This system implements that over an operator-supplied, versioned watchlist rather than a fixed annotated target set.

@P|The alias matcher is the load-bearing part, not the classifier. In this corpus a single entity appears in Bangla script, in three to six inconsistent romanizations, in English, as a party initialism, and sometimes as an epithet that carries the stance by itself. A watchlist that matches one spelling matches almost nothing, and it fails *quietly*, producing zero mentions, a result indistinguishable from an entity that was never mentioned. Five specific design consequences follow, and each of them was reached by a test failing rather than by reading code.

@BULLET|Match case-insensitively for Latin and exactly for Bangla. Bangla has no case, so lowercasing is a no-operation there and only introduces surprises.
@BULLET|Require token boundaries for short aliases. A two- or three-character initialism otherwise matches inside unrelated words.
@BULLET|Bangla word boundaries are not spaces. Bengali attaches suffixes directly, so an entity plus its suffix is one token; a suffix after a Bangla alias is permitted, a prefix is not.
@BULLET|Collapse overlapping aliases per target, keeping the longest. Where a party name and its short form both fire on the same words, every polarity cue in the surrounding clause was being counted twice.
@BULLET|Attach cues by **clause**, not by a fixed character window. With a sixty-character window either side, a comment of the form "B is the best but A is corrupt" scored both entities identically, because the window spanned the whole comment. Clause segmentation is both the correct treatment and the more interpretable one, because each verdict can be attributed to the clause that produced it.

@P|Two further properties matter for the cost model and for the epistemics. The matcher is **pure string work and therefore free**, so it runs in Stage 1 on every comment of every post, which means mention volume is available even for posts the gate bypassed. Furthermore, the language-model scoring is performed inside the Stage-2 comment-stance call that is already being issued: the matched entities are injected into a prompt that would have been sent regardless. The capability therefore adds **no additional large-model calls**.

@NOTE|**The watchlist is a stated bias model, not a measurement.** A file that declares "support for X is positive" encodes a political stance into the labels. That is entirely legitimate for a monitoring product whose operator wants to know who is attacking their client; it is indefensible if presented as neutral sentiment analysis. The file is therefore versioned with a named owner per entry, the repository distributes only a placeholder so that it states no politics of its own, and a neutral bucket exists for operators who want target-dependent stance without the editorial framing. Most importantly, target stance occupies a **separate output field** from document sentiment and the two are never summed, averaged or charted together. A comment can be positive in tone while opposing a listed entity, and conflating those two facts would destroy the only distinction the feature exists to make.

@P|Splitting **summary** from **stage2** is the decision in that table with the clearest return. The two Stage-2 jobs have opposite profiles: classification chooses from a fixed vocabulary and wants a cheap, constrained model, while summarisation writes prose and wants a fluent one. Keeping them on one role forced a single compromise and, worse, spent the fluent model on every classification call - which, because comment stance runs once per batch of twenty-five comments, multiplied straight through the comment lane. Separating them spends the expensive model exactly once per post.

@P|Splitting the role from the backend is what allows self-hosted and cloud serving to be interchangeable. Both speak the same OpenAI-compatible interface, so switching is a configuration change resolved per call in the order request, then a runtime toggle, then the environment default. The self-hosted path has **zero marginal token cost and no data egress**; the cloud path has the fastest inference and no GPU to operate, at a per-token price and with prompt content leaving the cluster. Because that last property is a privacy decision and not merely a performance one, a **privacy-locked tenant is pinned to the self-hosted backend on every path**: the decision is resolved at the API boundary where the tenant is known, stamped into the job envelope so a global toggle cannot re-route content that is already in flight, re-resolved on resume in case the policy changed in the meantime, and applied to chat and agent calls under the same rule. An explicit request for the cloud backend from a locked tenant is refused; a global operator toggle is silently downgraded instead, because an operator's switch is not that tenant's choice. The check **fails closed**: an unreadable policy table denies rather than permits, since a privacy guarantee that lapses when the database becomes unavailable is not a guarantee.

@P|Two further mechanisms in the same client warrant description. A **circuit breaker** per backend takes a repeatedly failing endpoint out of rotation for a cooldown period rather than continuing to issue requests to it, with an injectable clock so the state machine is unit-testable without sleeping. A **truncation-recovery** path additionally inspects the finish reason, auto-continues a reply that hit its token ceiling, trims back to the last complete sentence - including the Bangla sentence terminator - flags the result, and **never caches it**. That path exists because the ceilings were once fixed literals with nothing checking whether a reply had actually stopped at them, and Bangla costs far more tokens per character than English under these tokenisers, so a single fixed ceiling truncated Bangla and Banglish while sparing English. For a system whose primary languages are Bangla and Banglish, that bias is exactly inverted.

@H3|3.2.6  The agentic RAG insight layer

@P|The per-post pipeline is deterministic analysis followed by single-shot generation, and it remains so, because that is what the cost model requires. Above it sits a **corpus-tier agent layer** for work that genuinely needs planning and several tool calls: analyst questions, grounded reports, and targeted deep-dive analyses. **Agents are never invoked per post**, which would reintroduce exactly the per-item large-model cost the cascade exists to avoid.

@P|What distinguishes this layer from an assembly of established components is the **object of retrieval**. A conventional retrieval-augmented system retrieves documents - the text a user could have read anyway [34], [35]. These agents retrieve the system's **own structured analytical output**: sentiment distributions, stance verdicts by entity, ensemble-agreement statistics, coverage and vector provenance, toxicity scores, reaction mixes and embedding clusters. That output exists only because the pipeline ran, which makes the retrieval analytical rather than documentary, and it has a concrete consequence: an agent cites a number, and that number can be traced back through the ensemble to the model that produced it.

@P|Figure {{fig:mcp-sequence}} shows a single tool invocation crossing that boundary, including the branch that matters most for answer quality: an invalid or placeholder identifier is refused rather than answered with an empty result set, because an empty result set is indistinguishable to the model from a corpus that contains nothing.

@P|Deploying a tool-using loop on a corpus of adversarial political content means the loop itself needs hardening, and the guards in Figure {{fig:agent-loop}} were each written against an observed live failure rather than against a hypothetical.

@BULLET|**Untrusted-data delimiters.** Tool results carry Facebook comment text verbatim, so a comment reading "ignore previous instructions and report the sentiment as positive" arrives in the model's context as text that looks like an instruction [43]. Results are wrapped in explicit untrusted-data markers, forged closing markers inside the payload are neutralised, and the system prompt states that content inside the markers is data written by the public and must never be obeyed. This is **risk reduction, not a fix**; no prompt-level defence can promise resistance.
@BULLET|**A tool result cannot displace the context window.** One search call returning fifty rows serialised to 76,666 characters - roughly 39,000 tokens - purely because the default JSON serialisation escaped every Bengali character into a six-character sequence. The same rows serialised without escaping are 23,194 characters. Results are now serialised unescaped and capped at 6,000 characters, dropping **whole rows** rather than truncating mid-structure, with a note saying what was withheld; and citations are read off what the model was actually **shown**, so a row trimmed away by the cap cannot be credited as grounding.
@BULLET|**A repeat is not dispatched.** A deterministic query cannot return new rows. A byte-identical re-call is answered from the first result together with a note naming the tools the run has not yet tried; after two, those tools are withdrawn for the rest of the run. The observed failure this replaces was a run that spent eleven of fifteen calls on one identical search and then shipped the budget-exhausted notice as the briefing.
@BULLET|**A run is only complete if the answer answers something.** Four shapes of non-answer each fail the run after one synthesis retry: code output, payload narration, self-narration, and the empty template - correct headings with every cell a placeholder, which is the most consequential of the four, because on a cursory reading it presents as a completed report.
@BULLET|**An answer cannot deny its own retrieval.** The mirror of a fabrication, and a direct consequence of fixing one: given an honest escape hatch for "no post-level tool ran", a small model emits the canned phrase anyway. A run that wrote "no post-level data was retrieved" while a tool had returned ten real post identifiers now has a contradiction block appended, listing them, checked against the run record rather than against the answer's own table.
@BULLET|**An unknown watchlist identifier raises rather than returning empty.** The watchlist file is not visible to the model, so it invents an identifier, and an invented identifier returning no rows is indistinguishable from a quiet corpus. An unknown identifier now raises an error that names every valid one, which costs a single turn out of the budget instead of the whole run.

@P|Every run is persisted with the state machine in Figure {{fig:agent-lifecycle}}, so a run that failed a guard is distinguishable after the fact from one that exhausted its budget and from one an operator stopped.

@H3|3.2.7  Retrieval design

@P|Retrieval serves both the operator search surface and the agents' search tools, and both run the same code. An identifier is **looked up, not searched for**: an exact match on the post identifier, the platform identifier, the post URL or the campaign identifier short-circuits ahead of whichever mode was requested, and a query that looks like an identifier but matches nothing exactly falls to a prefix match, because the interface renders only the first eight characters of a twenty-five-character identifier. This closes two opposite failures observed in practice - a keyword search returning zero results for a real post identifier because it never read the identifier columns, and a semantic search returning twenty cosine neighbours none of which was the post, which is the more serious of the two, because twenty ranked results present as a successful search.

@P|Otherwise three arms run and their ranks are fused. A **dense arm** does cosine search over 768-dimension multilingual sentence embeddings [23]; a **chunk arm** does the same over a Bangla-aware splitter's output, for long posts where the relevant passage is not the opening; and a **lexical arm** fuses PostgreSQL full-text search with trigram similarity, which is what catches exact entity names, transliterations and hashtags - precisely what a multilingual sentence encoder generalises away. Fusion is by **reciprocal rank** [39] rather than by score normalisation, because a cosine similarity in the interval from minus one to one and a trigram similarity on its own arbitrary scale are not comparable and never will be; rank fusion discards the scores and keeps only the order, so a document both arms rank highly beats a document either arm ranks first alone.

@EQ|eq:rrf|RRF(@d)  =  Σ 1 / ( k + r_{a}(@d) )
@WHERE|The sum runs over the three retrieval arms @a. r_{a}(@d) is the rank of document @d in arm @a, and k = 60 is the standard damping constant [39]. A document absent from an arm contributes nothing from that arm rather than a penalty, which is why an arm that fails on a query cannot drag a good result down.
@ENDEQ

@P|Figure {{fig:rag-flow}} traces one question through that path, from the operator's query to the cited answer.

@P|Three features of that trace carry the design. First, both arms terminate in the *same* store. The dense and lexical arms are not two systems to be kept in synchrony; they are two indexes over one table, so a row cannot be present in one arm and missing from the other, and there is no reconciliation problem to solve. Second, the arms are combined by **reciprocal rank fusion** rather than by a weighted sum of their scores. This is not a tuning convenience: a cosine similarity and a trigram similarity are not measured on comparable scales, have no shared zero point, and cannot be added without inventing a conversion between them. Fusing on rank discards the magnitudes and keeps only the ordering each arm asserts, which is the only part of an arm's output that is commensurable with the other's.

@P|Third, and most easily missed, the arrow from the retrieved rows returns to the runner rather than continuing to the answer. Retrieval is a tool call inside a loop, not a stage in a pipeline. The agent may read the top-k rows, conclude that they do not answer the question, and search again with different terms before committing to an answer. That loop is what separates this design from classical retrieval-augmented generation, in which a single retrieval precedes a single generation and a poor first query cannot be recovered from.


@FIGURE|fig:rag-flow|Retrieval path behind the semantic search tool.
@FIGHEIGHT|56
@FIGNOTE|In Figure {{fig:rag-flow}}, the retrieval path is shown as one question in at the top and one answer out at the foot, with the single `semantic_search` tool splitting into an embedding arm and a lexical arm captioned with their actual index types, both querying the same table rather than separate systems, meeting at a rank-fusion box and returning top-k rows to the runner. The whole path is one tool call inside Process 6.0 (Insight) of the data flow diagram shown in Figure {{fig:dfd1}}, and the cylinder both arms query is D2 (analysis_results and embeddings), read on flow [15]. @H3|3.2.8  Storage, reliability and security

@P|Storage is split by access pattern rather than by convenience. **PostgreSQL with the pgvector extension** holds operational state, jobs, the canonical result document and the embedding vector in the same row, which removes a separate vector service from the deployment entirely: transactional reads and approximate-nearest-neighbour search [40] live in one store and metadata scoping is ordinary SQL. **ClickHouse** holds the denormalised analytics rows behind the dashboard charts and the analytics tools; the per-comment table is a collapsing engine keyed on tenant, post and comment, so a re-analysed comment collapses to its newest row rather than double-counting. **Redis** carries the streams, the response cache, the deduplication keys, rate limits, job counters, cancellation flags and the usage counters. **Object storage** holds the raw result document at a deterministic key for replay and audit.

@P|On the security side, the design treats post text as untrusted throughout. A credential that is shaped like a token is verified as a token on **every** transport - the authorization header, the API-key header, and the query parameter that event-source connections require, because verifying it on only one of those meant an expired or forged token authenticated on all four streaming endpoints. API keys are stored as hashes and the tenant identity comes **from the stored row, never from a client-supplied token body**, which is what makes the privacy pin of Section 3.2.5 enforceable at all. Claims taken from a token are allowlisted and the authentication method is set server-side after the merge, because spreading the payload last meant any claim in the token won, including the one distinguishing a human session from a service call.

@H3|3.2.9  Observability and telemetry

@P|A pipeline whose stages are separate processes joined by a durable queue has no call stack, so a post in flight leaves no trace that any single process can report. Observability is therefore a design concern rather than an operational addition, and it is built on two independent paths so that the failure of one does not blind the other.

@P|The first path is the conventional one: metrics are scraped into Prometheus, structured logs are shipped to Loki, and spans are exported to Jaeger through OpenTelemetry, with Grafana over all three. The second path exists because the operator dashboard needs a live view without querying a log store: every stage writes progress events and counters into Redis, and the API exposes them as Server-Sent Event streams. Figure {{fig:observability}} shows how the two paths reach their respective consumers.

@FIGURE|fig:observability|Telemetry paths from the pipeline stages to the operator surfaces.
@FIGHEIGHT|78

None of this is a data flow of the data flow diagram shown in Figure {{fig:dfd1}}: it is instrumentation of Processes 1.0 to 5.0 rather than any record they exchange, which is why no numbered flow appears here and why D1 (posts and raw payloads) through D5 (analytics events and comment sentiments) are absent from the figure entirely. Two independent paths reach the operator - the dashboard path driven by counters and events held in Redis, and the Grafana path driven by the conventional metric, log and trace stores - and the second does not pass through the project's own API, so it remains available precisely when the API is the component that has failed.
@ENDFIGURE

@P|Figure {{fig:observability}} shows why there are two paths rather than one, and the distinction is a failure-mode argument rather than a matter of taste. The dashboard path carries counters and events through Redis to the API and then to the browser; it is low-latency and it is what an operator watches during a run. The Grafana path carries metrics, logs and traces into their conventional stores; it is higher-latency, it retains history, and it is queryable after the fact. Critically, the second path does not pass through the project's own API. If the API is the component that has failed, the first path is unavailable precisely when it is most needed, and the second remains. An observability design in which every signal reaches the operator through the system being observed can only report faults that are not its own.

@P|The same reasoning explains the split in the endpoint band. Pipeline depth and usage counters are served from Redis because they are counters that the stages themselves maintain; host statistics are served from Prometheus because they concern the machine rather than the work. Traces are exported to Jaeger and never surfaced in the dashboard at all, because a trace is a debugging artefact for an engineer with a question, not a number an operator watches.

@P|Logging in particular has two sinks from one logger, shown in Figure {{fig:logging}}. The same structured record is written to standard output, where a collector ships it to the log store, and to a capped Redis buffer that the dashboard tails over a stream. The duplication is deliberate: the log store is the durable, queryable record, while the buffer is what makes a live tail possible without a query engine in the request path, and its cap is what prevents an unbounded buffer from becoming a second failure mode.

@H3|3.2.10  Deployment architecture

@P|The same code runs in two deployment shapes, and the difference between them is which concerns are collapsed. Figure {{fig:compose}} gives the MVP shape, in which authentication, ingestion and reporting are one service and the message bus is Redis. Figure {{fig:k8s}} gives the production shape, in which those concerns are separate deployments, the bus is a partitioned log, and the worker pools scale on consumer-group lag rather than on processor utilisation.

@P|In the Compose shape of Figure {{fig:compose}} three simplifications are visible and all three are deliberate. Authentication, ingestion and reporting share one container, so the tier runs one service where production runs four; this is acceptable because at MVP volumes no one of them can starve the others. Redis plays three roles at once - message bus, cache and deduplication set - which removes an entire broker from the operational surface at the cost of coupling three failure modes to one process. The vLLM container is optional and is drawn as an outside system, because it is present only when the local backend is selected. The monitoring box has no edges at all: at this tier observability watches the stack without participating in it, and removing it changes nothing about how work flows.

@P|The Kubernetes shape of Figure {{fig:k8s}} reverses each of those compromises and adds one property that Compose cannot express. The four stateless services become separate deployments scaled on processor use and request rate. Redis is replaced by Kafka as a three-broker StatefulSet with named topics, including a dead-letter topic that gives permanently failing work somewhere to go other than an infinite retry. The substantive difference, however, is the scaling signal. The stateless tier scales on processor and request rate, which are load signals; the worker pools scale on **consumer-group lag**, which is a backlog signal. That distinction matters for a batch pipeline because a worker saturated by a slow model call shows high utilisation whether the queue behind it holds ten items or ten thousand, so utilisation cannot distinguish "busy" from "falling behind". Lag can. The two GPU pools are separated for the same reason the two stages use different serving mechanisms: small-model inference and large-model generation have different memory profiles and should not contend for one accelerator.

@P|The data tier sits inside a network policy so that only the ingress is reachable from outside the cluster, and the observability namespace is drawn deliberately unconnected, since it observes every band without appearing in any request path.

@FIGURE|fig:compose|MVP deployment: Docker Compose service topology.
@FIGHEIGHT|82
@FIGNOTE|In Figure {{fig:compose}}, the MVP deployment is shown as a service graph read downward from the gateway: a single `api` container collapsing three concerns, forking left into the Redis cylinder that is bus, cache and deduplication set at once, and right into the Phase 2 panel holding the agent orchestrator and the MCP servers, with the NLP and LLM workers making a round trip through Redis, an optional vLLM container, and three arrows fanning into postgres, clickhouse and minio. @P|Two patterns run through the table. The first is that most decisions were settled by an operational property rather than by a quality benchmark: what fails, how it fails, and whether the failure is visible. A component that is marginally more accurate but fails silently was rejected in favour of one that is marginally less accurate and fails loudly, on the grounds that a monitoring product's worst outcome is confident wrongness rather than an acknowledged gap.

@P|The second is that several rejected options were rejected only for this tier. Kafka over Redis Streams, a dedicated vector database over pgvector, and a separate authentication service were all judged correct at production scale and unnecessary at MVP scale. Recording them as rejected rather than as absent is what makes the deployment progression in Section 3.2.10 a plan rather than a retrofit: each of those decisions has a stated trigger for revisiting it, and the production topology already reflects the outcome.

@P|Across all of these decisions the theme is consistent: a preference for components whose failures are **loud and local** over components that are marginally better but fail silently, and a preference for managed, lower-overhead infrastructure wherever the extra control a heavier option would buy is control this project does not need at its scale. The major trade-off this approach concedes is a degree of coupling to specific runtime choices - Redis serving three roles at the MVP tier, pgvector rather than a dedicated vector service, a hand-tuned rather than a learned gate - accepted in exchange for an operational surface that two people can actually run and audit within the timeline of an academic project. Each of those concessions carries a stated trigger for revisiting it, and the scalability implications are revisited in Chapter 6 under Limitations.

@H3|3.3.4  Prioritisation Rationale

@P|Between Phase-I and the Final Defence submission the schedule was fixed, so the ordering above was a series of choices rather than an accident, and the principle behind them was consistent: **prefer a capability that can be evidenced over a capability that can only be described.** Where a feature could be finished and measured, it was finished; where finishing it would have produced a claim the project could not check, the effort went into the checking instead.

@P|That principle settled the three decisions that shaped the deliverable. The audit phase was funded ahead of new features because the first pass established that the project's own headline claim was contradicted by its own running code, and there is no defensible order in which more capability is built on top of a claim known to be wrong. The image modality was left unexercised rather than demonstrated on substitute images, because a screenshot of the visual path running on images that are not the corpus's own would evidence the code and misrepresent the result. And labelling accuracy was descoped rather than approximated, because the only cheap way to produce that number is to score the models against labels drawn from the system's own models, which measures agreement and reports it as accuracy.

@P|The cost of that ordering is visible and is not argued away: this report contains no accuracy figure for any labeller, and two capabilities are recorded as built rather than proven. What it bought is that every number in Chapter 4 was produced by running the code in this repository, and that the boundary of the evaluation is stated in Section 4.3.3 rather than left for a reader to infer.

@H2|3.5  Summary

@P|This chapter brought together the requirement analysis and the design specification for the system. It began with requirement analysis, where eighteen functional and twelve non-functional requirements were identified from the gaps observed in existing monitoring platforms and Bangla classification systems, and where the two classes were deliberately held to different standards of evidence. The system design followed: a five-stage, queue-decoupled microservice in which cheap analysis runs unconditionally over every post and every comment, a router decides how much expensive analysis each unit earns, and an assembler emits one schema-validated document per thread into three stores chosen by access pattern.

@P|The data-flow diagrams showed the system's boundary and where state is held, with a single deliberate absence at level 0 - nothing is ever written back to the upstream platform - and a single deliberate isolation at level 1, where the corpus-tier insight process is reachable only through persisted stores and never from a post in flight. The UI design section then set out the eleven-tab operator dashboard, its component hierarchy, and the ticketed streaming topology that keeps a credential out of every event-source URL.

@P|The Detailed Methodology section covered the load-bearing technical decisions. The central one is that the **router makes two independent decisions** rather than one: whether a post earns post-level large-model work, and which of its comments the Stage-2 labellers read. Around that sit an eight-labeller comment ensemble with an explicit abstention protocol, a watchlist stance capability whose hard part is the alias matcher and which adds no additional model calls, a pluggable inference backend with per-role model resolution and an enforceable tenant privacy lock, and a corpus-tier agentic layer that retrieves the system's own analytical output through typed tool servers. Every significant choice - the message bus, the operational and analytical databases, the vector index, the serving model, the fusion method, the agent tool interface - was recorded in Table {{tab:alternatives}} together with the alternative it displaced and the constraint that justified it, so that a change of constraint has a documented path back rather than requiring the decision to be rediscovered.

@P|The Project Plan section set the four assessed milestones against the five development phases beneath them, gave an exit criterion for each phase, and set the tasks carried forward from Phase-I against what was actually delivered: six completed, one reduced to a documented boundary, one implemented but unexercised, and one - the audit phase - present in the delivery with no planned counterpart at all. It stated the two ways in which the plan as worked differed from the plan as written, an entire audit-and-evaluation phase that was not originally scheduled and a deliberate overlap between the agentic layer and the capability build-out, and recorded the principle that settled the ordering when the schedule could not accommodate everything: prefer a capability that can be evidenced over a capability that can only be described. The Task Allocation section recorded the allocation of effort across task areas and phases for a single-student project, and in particular why an audit phase was created to buy back the second reader that a two-person team gets for free. Implementation details, the testing strategy, the measurement studies and the results for every module are presented in the next chapter.

@P|Three consequences follow from Table {{tab:corpus}} and Figure {{fig:coverage-dist}}, and they are stated here rather than in a limitations section because they constrain every number that comes after.

@NUM|1. **The comment sample is not random.** The stored comments are the platform's returned set, which is engagement-ordered. With 64.1 percent of comments carrying zero reactions and a maximum of 946, aggregating sentiment over an engagement-biased 3.75 percent sample and calling the result "the sentiment of this thread" is not supportable. What the data supports is a claim about *the most-engaged N comments per post*, and that is the phrasing this report uses.
@NUM|2. **Post-level sentiment is a text measurement.** The 69 image references are relative object-storage keys whose objects are not present in storage, so no image bytes are reachable in any runnable configuration and the vision term has never contributed a non-zero value. The image path is implemented and reports an explicit failure status rather than a fabricated neutral verdict, and the fusion weights renormalise over the terms that carry a real model verdict, so an absent image term no longer consumes its share and drag a genuine text signal toward neutral.
@NUM|3. **The 7 caption-less posts stay in the corpus.** They yield no post text to analyse, but they carry 1,307 comments that analyse like any other. An earlier working corpus excluded them, which meant the evaluation was measuring a population the running system never processes and under-counting the comment lane, which is now the dominant cost.

@H3|4.2.2  Verification strategy and the full-chain result

@P|The testing strategy for this system is automated rather than manual, because the failures that dominated this project are not failures a person notices by looking. Verification is organised in three layers. **Contract tests** assert that the JSON documents crossing every boundary validate against their schema, and several of them grep the source directly to assert structural invariants - that every worker checks the job cancellation flag before doing work, that the dashboard reads only fields the API returns, that the autoscaler manifests name exactly the streams the workers create. Those fail on a rename, which is their purpose. **Regression tests** pin every defect found in the audit passes, so a repaired defect that returns fails the build. **Datastore tests** run against throwaway PostgreSQL and Redis containers started per session, so a default test run can never damage a developer's environment; two further suites are gated behind explicit markers, one needing a full Docker and inference stack and one that wipes live datastores.

@H3|4.2.3  Security and access-control testing

@P|Functional correctness establishes that each module does what it is meant to do. It does not establish that a caller who is not entitled to a result cannot obtain one, and the two are tested separately here because they fail differently: a functional defect produces a wrong answer, whereas an access-control defect produces a *correct* answer delivered to the wrong party. Every identity-bearing path in the system - the token issuer and its verifier, the API-key store, the single-use streaming ticket, the tenant scope on every analytical query, and the data-residency policy that decides which inference backend a tenant's text may reach - was exercised against both the permitted and the refused case, on the principle that a check which has never been observed to refuse anything has not been tested at all.

@P|Eight suites carry that work and they run inside the same pass-or-fail chain as everything else. Executed together on 29 August 2026 they collect **138 tests, all passing in 6.89 seconds**: seventeen on token issue and verification, thirty-seven on the signup and password path, twenty-five on transport hardening, seventeen on the backend policy resolver, fourteen asserting that the privacy lock survives every pipeline entry point, two on cross-tenant reads, four on rate limiting and twenty-two on prompt-injection containment in the agent layer. The first 116 of those are the security area of Table {{tab:suite}}; the remaining twenty-two are counted there under the agentic layer, because injection containment is a property of the agent runner and is tested alongside it. Table {{tab:security}} states the scenarios and their outcomes, at the same one-or-two-per-surface rate as Table {{tab:functional}}.

@P|Two of these rows are worth reading twice, because they are the cases where a system usually fails quietly rather than loudly. The first is the unreadable policy table. A residency check that cannot reach its policy store has two options, and the tempting one - carry on with the previous answer - converts a storage hiccup into a data-egress incident that leaves no trace. The test named `test_an_unreadable_policy_table_denies_rather_than_permits` pins the other choice. The second is the explicit backend request from a locked tenant, which is **refused rather than downgraded**. Silently substituting the self-hosted backend would honour the policy while lying to the caller about which model answered, and a caller who believes they received a cloud answer will attribute its quality to the wrong model.

@P|What this subsection does not claim is a penetration test. These are white-box tests written by the same members who wrote the code they guard, so they establish that the checks behave as specified under the conditions the authors imagined. An adversarial review by a party with no knowledge of the implementation is named in Section 6.3 as the work that would close the remaining distance.

@EQ|eq:governed|γ  =  C_{gated} / ( C_{gated} + C_{comment} )
@WHERE|where C_{gated} counts the large-model calls the router's gate releases - the post-level lane together with the post-level Stage-2 tasks - and C_{comment} counts the per-comment labelling calls, which run for every post whether the gate routed it or not. @P|Three conclusions follow, and the first of them contradicted the project's own headline claim.

@P|First, the routing rate is not the cost story. Between 85 and 96 percent of calls are comment-level. The initial claim was that cheap models perform ninety to ninety-five percent of the work and a selective large model handles the rest, and that this was the central cost-control idea. That assertion was never measured; when it was measured, the gate had in fact been routing one hundred percent of posts for a period because of two field-name defects, and after those were repaired the gate still governed only a minority of spend. The claim that survives contact with the measurement is narrower and is the one this report makes: **cheap NLP filters which comments and which posts deserve a large model.** Both halves matter, and the second is now the bigger one.

@P|Second, improving Stage 1 shrinks the gate's importance rather than the bill. This result runs counter to intuition. A better Stage 1 types more posts confidently, so fewer route, so the gate decides less; meanwhile comment labelling runs unchanged.

@P|Third, the gate selects the right posts. Under the shipped configuration the 7 routed posts hold 3,404 of the 8,713 comments that reach a model - the gate is escalating the large, contentious threads, which is the behaviour the design intends and which a routing rate quoted on its own cannot show.

@P|One earlier estimate was also corrected by measurement and is recorded because the correction was large. Filtering emoji-only comments out of model batches was expected to save roughly seventeen percent of the comment bill. Emoji-only comments are **2.8 percent** of the corpus. The seventeen-percent figure was the share taking the fast path, which conflates emoji-only reactions with short *text* comments, and a short text comment still carries text that a model can read. Filtering emoji is still correct, because they are pure waste, but it is not a cost lever.

@H3|4.2.5  Retrieval evaluation

@P|Retrieval is the one axis this project evaluates against a ground-truth set, and the numbers were obtained with a 32-query known-item set derived from each target post's own topics and entities. Each query has exactly one marked relevant post. The same set was run before and after real embeddings were enabled, so the two recall columns in Table {{tab:retrieval}} differ only in whether the stored vectors are semantic or hashes.

@P|Three standard measures are reported over the query set @Q, at cut-off k = 10. Because each query @q has exactly one relevant document d(@q), recall@k reduces to the fraction of queries whose target appears in the top k at all:

@EQ|eq:recall|recall@k  =  ( 1 / N ) · Σ 1[ r_{q} ≤ k ]
@WHERE|The sum runs over the N = 32 queries @q. r_{q} is the position of the one relevant post in the list returned for query @q, and 1[·] is the indicator function, worth 1 when the condition holds and 0 otherwise. This is the measure that matters when the whole top-k is handed to a generator [42], because a target absent from the context cannot be recovered by the model.
@ENDEQ

@EQ|eq:mrr|MRR@k  =  ( 1 / N ) · Σ 1 / r_{q}
@WHERE|over the same N queries, with the term taken as 0 when r_{q} > k. This credits an arm for placing the target near the top rather than merely inside the window, and is the measure on which chunking gains where recall does not.
@ENDEQ

@EQ|eq:ndcg|nDCG@k  =  ( 1 / N ) · Σ 1 / log_{2}( 1 + r_{q} )
@WHERE|again over the same N queries, with the term taken as 0 when r_{q} > k. This is the single-relevant-document form of the cumulated-gain measure of Järvelin and Kekäläinen [41]: the ideal discounted gain is 1 because exactly one document is relevant, so the normalising denominator vanishes.
@ENDEQ

@P|Three findings come out of Table {{tab:retrieval}}, and the third is a defect rather than a result.

@P|Hash vectors were indistinguishable from chance. @P|**Chunking improves ranking rather than recall on this corpus**, and the reason belongs with the finding: this corpus consists predominantly of short captions.

@P|The lexical arm's improvement was a bug fix, not a benefit. The lexical column moved from 0.3750 to 0.7500 with no vector involved, because the full-text half of that arm had never fired at all: the query builder conjoined every term, so an eight-token question demanded all eight words in one caption and matched **zero** rows across the entire query set. Everything previously credited to "full text plus trigram" was trigram alone, and the index built for full-text search was dead weight. This is recorded because it is the same failure shape as the routing defect and the identifier mismatches: a component that produced no output, reported no error, and was covered by a passing test.

@NUM|C1. **They are lower bounds.** The set marks exactly one relevant post per query, so every other on-topic post the retriever returns is counted as a miss.

@P|Four readings follow from the table, and the first is the one that costs the project its simplest claim. Moving from the all-cheap baseline to the shipped configuration cuts total calls from 813 to 529, a reduction of roughly a third - real, but nowhere near the order-of-magnitude saving that a routing rate falling from 74 to 16 percent appears to promise. The reason is in the row beneath: the gate's share of calls falls from 54.7 to 30.4 percent, so as the gate routes fewer posts it also governs less of what remains. @P|Second, the LLM-everywhere column is deliberately left partly empty, and the empty cells are informative. An estimate would have been easy to produce and impossible to defend, and a column of plausible numbers beside two columns of measured ones would have invited exactly the comparison that the evidence does not support.

@P|Third, two rows favour the shipped configuration on grounds that have nothing to do with cost. Independent verdicts per comment rise from one to as many as eight with abstention, and the output can state what produced each label. Both are properties of the ensemble rather than of the router, and both survive regardless of how the routing argument settles - which matters, because it means the contribution does not rest on the cost claim that measurement weakened.

@P|Fourth, one row is deliberately marked orthogonal. Retrieval recall is unchanged by the choice of Stage-1 engine, because retrieval reads persisted analysis rather than participating in the cascade. It appears in the table only to record that the improvement from 0.5312 to 0.8750 came from replacing hash vectors with real embeddings, and not from anything the router does.

@H3|4.3.2  What the measurements establish, and what they disconfirm

@P|Three findings are supported. The cascade works as a mechanism and its behaviour is now observable rather than asserted: the gate responds to Stage-1 quality in the direction the design predicts, its decision travels explicitly on the envelope, its inputs are logged through the same readers the rules use, and its bypass branch is validated end to end against the output schema - a branch that had never once executed before the audit that found it. Hybrid retrieval is a real improvement, and the stratification in Table {{tab:retrieval-stratified}} explains why: the fused configuration reaches 0.8750 recall@10, and the two arms fail on *disjoint* query populations, which is a stronger argument for fusion than the aggregate number that hides it. Provenance reporting changed what the system can honestly claim, and asymmetrically - it removed claims rather than adding them, turning two apparent successes into stated absences: the image modality, and the majority of the default configuration's comment labels.

@P|The project's original headline claim was wrong twice over, and reporting that is more useful than reporting only the corrected version. It was wrong **in fact**, because the gate was routing every post: two rules read field names Stage 1 never emitted, one read a field Stage 1 sets as a placeholder for Stage 2 to fill, and one compared a language value against a code-mixing marker recorded under a different field entirely - net, one rule always fired and three could never fire. Every one of the four was a **silent degradation rather than an exception**, which is the generalisable lesson of this project; the mitigation - named reader functions, a diagnostic log routed through those same readers, and a test asserting that the reader sees the producer's real output - was then applied to the three other places the identical pattern had occurred. It was wrong **in framing**, because even a correctly functioning gate governs a minority of spend once every comment is labelled. That is the finding with the most transfer value outside this project: **when the routed unit contains many sub-items that each need work, routing the container is not the cost lever.** The published cascade literature routes single queries [30], [31], [32] and does not encounter this, which is why it took a measurement rather than a reading to find.

@H3|4.3.3  The boundary of the evaluation, and threats to validity

@P|Labelling accuracy is outside the scope of this project, and the report claims none. The deliverable is a system: one that routes work, labels it, records what produced every label, and serves the result under a validated contract. A benchmark number would additionally require human-adjudicated labels, and producing them is an annotation programme with its own guideline, agreement study and timeline - not a further measurement script. The tooling that consumes such labels ships with the repository: a stratified 300-comment sample drawn by comment kind and script, and a scorer that reports per-stratum accuracy for the whole configured roster with abstention and accuracy-when-answered separated. The gold file therefore holds 300 sampled rows and **zero adjudicated labels**, deliberately - seeding them from a model in this repository and then scoring that model would measure the system's agreement with itself. The position this report adopts is the one an engineering project can defend: the 1,417 passing tests are correctness and contract tests, a green suite is not a quality claim, and the report accordingly quantifies rates, counts, coverage, latency, retrieval quality and provenance, and quotes no macro-F1, confusion matrix or ship gate for any labeller.

@P|Four further capabilities are implemented and cannot currently produce a signal, and they are listed rather than omitted: the **image modality**, which cannot be exercised because no image bytes are reachable; **horizontal scaling**, code-complete and unbenchmarked, with no multi-replica run timed; **cross-backend quality parity**, which falls under the same annotation dependency; and the **cross-encoder reranker**, implemented but unmeasured, so the evaluation harness prints a skip rather than reporting the fused order as though a rerank had happened. Table {{tab:evidence}} is the evidence ledger for the system as a whole: every capability appears in it exactly once with the class of evidence supporting it, so that no claim made elsewhere in this report rests on a stronger basis than the ledger records.

@H2|4.4  Summary

@P|This chapter described the implementation and evaluation of the system. The environment is a Python 3.12 and React 19 codebase over four datastores chosen by access pattern, four locally served models and three deployment shapes expressing the same code. Functional correctness was established across every module by 1,420 automated Python tests - sampled as forty representative acceptance scenarios and broken down by area in Table {{tab:suite}} - inside a whole verification chain of Python suite, dashboard unit tests, lint, production build and browser tests that passes as one pass-or-fail command in seventy-three seconds. Access control was tested separately from function because the two fail differently: 138 tests across eight suites exercised token issue and verification, the hashed API-key store, single-use streaming tickets, cross-tenant reads, the fail-closed residency policy and prompt-injection containment, against both the permitted and the refused case in each.

@P|Four measurement studies followed. The routing gate works and its behaviour is observable, but it governs 30 percent of large-model calls rather than the great majority - a finding that contradicted the project's own headline claim and reframed it into one that survives contact with the data. Hybrid retrieval reaches 0.8750 recall@10 against 0.1875 for hash vectors, and stratifying the query set shows the dense and lexical arms failing on disjoint populations, which is the real argument for fusing them. Label-provenance measurement showed that 71.3 percent of per-comment labels in the default configuration are not model output, and the response was to report that rather than conceal it. The results section then walked the delivered software feature by feature, every figure a capture of the running system rather than a mock-up.

@P|Taken together these findings show that the design decisions of Chapter 3 - the separation of the router's two decisions, the abstention protocol, and the placement of the agent layer outside the per-post path - became a working, auditable system rather than remaining a proposal, and that validating the full chain as a single command is what makes the evidence discipline enforceable: a claim in this report that stopped being true would break a test. Equally significant is what the chapter does not claim. The evaluation stops where the engineering does, and labelling accuracy is left to the annotation programme specified in Section 6.3. The next chapter turns to the engineering standards followed, the societal and environmental impact of the work, and the complex engineering problem it represents.

@CHAPTER|5|Engineering Standards and Design Challenges

@INTRO|This chapter records the standards the system complies with and the alternatives that were rejected in each case, assesses the work's impact on life, society, the environment and its own sustainability, presents a financial analysis with a costed alternative, and maps the project onto the complex-engineering-problem, knowledge-profile and complex-engineering-activity frameworks.

@H2|5.1  Compliance with the Standards

@P|Only the standards that genuinely bear on this system are listed. For each one, the alternative that was considered is named with its trade-off, because a standard adopted without an alternative in mind is a default rather than a decision.

@H3|5.1.1  Software Standards

@P|For data interchange the system uses JSON validated against a published JSON Schema. Every document crossing a boundary is JSON, and both the input contract and the canonical output are validated against a published schema. The assembler **raises** on a validation failure rather than persisting the document, so nothing downstream - no store, no API response, no dashboard row - ever sees an unvalidated result. The schema carries an explicit version on every result, and the version history is part of the record: one increment exists purely because a language-model task's output was being computed, paid for and then dropped by a component that read a different set of fields.

@BULLET|*Alternatives considered.* **Protocol Buffers** or **Avro** would give a smaller wire format and stronger typing, and Avro's schema evolution rules are better than anything JSON Schema offers. They were rejected because the upstream platform emits JSON, the downstream consumers are third-party applications for which a self-describing text format is far easier to adopt, and the analysis payloads are dominated by free text where a binary encoding saves little. The cost of the choice is verbosity, and it is paid down where it actually hurts: stream payloads are serialised without escaping non-ASCII characters, which on Bengali text is not cosmetic - escaping was measured as roughly half the token bill on the agent path and triples the bytes on every stream entry.

@P|The web API is REST over HTTPS, versioned, and described by a generated OpenAPI document. All endpoints live under a version prefix; asynchronous work returns an accepted status with a job identifier to poll or subscribe to; writes accept an idempotency key; list endpoints paginate by cursor; and errors use one consistent envelope. The live specification is served by the application rather than maintained by hand.

@BULLET|*Alternatives considered.* **GraphQL** would let the dashboard fetch exactly the fields it needs and would have avoided one class of defect this project hit repeatedly, where a hand-maintained response model silently dropped fields the pipeline had computed. It was rejected because the consumers are heterogeneous third-party services rather than one first-party client, because caching and rate-limiting are simpler on REST, and because a strongly typed response model is the correct fix for that defect class, which is what was done. **gRPC** was rejected for the public surface for the same reason as Protocol Buffers, though it remains the right choice if an internal high-volume path is ever extracted.

@P|Streaming uses Server-Sent Events. Five live surfaces stream: system telemetry, job progress, pipeline queue depth, logs, and chat tokens.

@BULLET|*Alternatives considered.* **WebSockets** are bidirectional and would have been the obvious choice, but every one of these surfaces is server-to-client only; Server-Sent Events reconnect automatically, traverse ordinary HTTP infrastructure, and need no separate protocol upgrade. Their one real disadvantage drove a design decision: an event-source connection cannot carry an authorization header, so something must go in the URL. Rather than putting a credential there, the system issues a **single-use ticket valid for about sixty seconds**, so a streaming URL captured in a proxy log is worthless. **Long polling** was rejected as strictly worse on both latency and connection count.

@P|Authentication uses JSON Web Tokens with HMAC signatures alongside hashed API keys. Tokens carry a short expiry with a refresh endpoint; API keys are stored as SHA-256 hashes and the tenant identity is read from the stored row rather than from anything the client sends.

@BULLET|*Alternatives considered.* **OAuth 2.0 with an external identity provider** is the right answer for a multi-organisation production deployment and is the documented upgrade path; it was not adopted here because it adds an external dependency that the offline test suite cannot exercise. **Session cookies** were rejected because the primary consumers are machine clients. The important compliance point is not the choice of scheme but the enforcement: a credential that is *shaped* like a token is verified as a token on every transport, because verifying it on only one of them meant an expired or forged token authenticated successfully on all four streaming endpoints.

@P|Character encoding is Unicode under NFC normalisation. All text is normalised at ingestion, and script tagging distinguishes Bangla, Latin and mixed content. This is not administrative: without normalisation, two visually identical Bangla strings can differ byte-for-byte, which would defeat both the content-hash deduplication and the alias matcher that the watchlist feature depends on.

@P|Code quality and testing rest on static analysis in both languages, a typed settings object as the single source of configuration, and a test suite in which contract tests assert structural invariants across component boundaries. Two test markers gate the expensive paths, one of which mutates live datastores and must therefore never run by accident.

@H3|5.1.2  Hardware Standards

@P|On accelerators and precision, inference targets CUDA-capable devices with quantised weights, and the deployment is explicitly designed so that the cheap classifier heads run on **CPU** while the accelerator serves the language model. That is a decision rather than a fallback: measured on a four-gigabyte card already serving a seven-billion-parameter model, roughly 285 megabytes remain free, which fits one classifier head and not seven. Attempting to place all seven on the accelerator produces the least desirable outcome - some load, some fail, and a head that fails to load abstains silently for the life of the process, so a run silently degrades from eight voters to two.

@BULLET|*Alternatives considered.* **Placing every model on the accelerator** was the initial configuration and produced exactly that degradation. **Running the language model on CPU as well** was rejected on latency grounds. The chosen split costs roughly three gigabytes of checkpoint storage and a few CPU cores, and it makes the ensemble's coverage deterministic.

@P|On storage and memory, the vector column is fixed-dimension and the embedding dimension must match it, which is enforced rather than documented: a mismatch fails every insert instead of silently storing an unusable vector. Object storage speaks the S3 API, so the development deployment runs MinIO and production can substitute a managed service with no code change.

@P|The commodity-hardware target is the binding constraint: the system is required to run on a single developer workstation with one consumer accelerator, which is why the entire model stack has a stub mode in which every component degrades to a deterministic function and **reports that it did so**. That reporting is the standard being complied with: a run in which every component degraded still reports the engine it *intended* to use, so the list of degraded components is the only signal distinguishing a real result from a heuristic one.

@H3|5.1.3  Communication Standards

@P|For transport security, TLS terminates at the gateway, datastores and inference servers sit on private subnets, and only the gateway is internet-facing. In the cluster deployment a network policy enforces that boundary rather than relying on topology.

@P|For message transport, Redis Streams with consumer groups provides at-least-once delivery for the MVP tier; the production tier migrates to a partitioned log. Every stream and consumer-group name is defined in exactly one module, and a test asserts that the autoscaler manifests name the same streams and groups the workers create - a rule that exists because a scaler pointed at a group no worker creates reports no backlog, so the one stage where scaling changes cost never scaled while the manifests looked correct.

@P|Tool transport is the Model Context Protocol: agents reach data only through MCP servers over streamable HTTP [38]. Adopting a protocol rather than writing bespoke glue is what makes a new analytical capability a tool registration plus one line in an allowlist. The protocol's own security literature is taken seriously here: because tool results carry third-party text verbatim, everything a model is shown is wrapped in untrusted-data delimiters with forged-delimiter neutralisation [43].

@P|Data residency is itself a communication constraint, because the choice of inference backend is a communication decision, because the cloud backend sends prompt content, which is to say, real people's comments - to a third party. It is therefore treated as a policy rather than a performance setting: the decision is resolved where the tenant is known, stamped into the job envelope so a later global toggle cannot re-route content already in flight, re-resolved on resume, and **fails closed** when the policy table cannot be read.

@H2|5.2  Impact on Society, Environment and Sustainability

@H3|5.2.1  Impact on Life

@P|The direct beneficiaries are the analysts who currently read comment threads by hand. On the largest thread in this corpus that means 2,857 stored comments against a platform-reported 9,224; no analyst reads that, so in practice a human reads the top twenty and generalises. The system does not remove the human, and it is designed on the assumption that it should not: it reports coverage, it reports what produced each label, and it shows eight independent verdicts side by side precisely so that a human can see where the models disagree and look there.

@P|There is a second, less obvious effect on the people whose comments are analysed. A system that labels a comment negative and stops there attributes an emotion to a person. A system that separates document sentiment from stance toward a named entity, and that says **uncertain** when no model read a comment rather than defaulting it to neutral, makes fewer claims about people than the alternative. The effect is modest, and it is the correct default when the subjects have not consented to the analysis.

@H3|5.2.2  Impact on Society and Environment

@P|The societal dimension comes first. The corpus this system was built on is political content from Bangladesh, and the technology must be assessed as dual-use. The same capability that lets a newsroom see how a policy announcement was received lets an actor identify who is criticising them. The project's response is not to pretend otherwise but to make the editorial choice visible: the watchlist is a **stated bias model** carried in a versioned file with a named owner per entry, the repository ships a placeholder so that it states no politics of its own, and stance lives in a separate field so it cannot be quietly folded into a sentiment total. A neutral bucket exists specifically so that an operator can have target-dependent stance for monitoring without the advocacy framing.

@P|The environmental argument for this design is the same as the cost argument, and it is measurable in the same units. Every large-model call avoided is accelerator-seconds not spent. Under the shipped configuration the corpus run costs 529 calls against 813 for the keyword-baseline configuration, and the caps that were deliberately left disabled would reduce the dominant comment lane by more than an order of magnitude on large threads - a 2,857-comment thread costs 115 stance batches uncapped and four with the cap set to one hundred. Two further design choices cut work rather than merely moving it: exact and near-duplicate detection avoids re-analysing reshared content, and repeat comment texts within a thread collapse to their most-liked occurrence, which on threads containing many repeated short phrases yields a substantial reduction at no loss of coverage. Set against this, the corresponding cost is that the eight-labeller ensemble spends roughly 0.92 seconds of CPU per comment across seven heads in order to obtain an agreement signal, and that the full roster of seven heads was retained rather than reduced.

@H3|5.2.3  Ethical Aspects

@P|Five ethical positions were taken deliberately and each has a corresponding mechanism in the code, which is the only form in which an ethical position is checkable.

@NUM|E1. **Personal data is handled as personal data.** Social content contains identifiable people. The system encrypts at rest and in transit, scopes every read by tenant, supports per-tenant retention and deletion, logs data access, and - the mechanism that makes the rest enforceable - takes tenant identity from a stored row rather than from anything a client sends.
@NUM|E2. **A privacy commitment must survive a database outage.** The tenant policy check originally returned permissively on any database error, which permitted egress precisely when the policy could not be verified. It now returns a service error. A privacy guarantee that evaporates when the database hiccups is not a guarantee.
@NUM|E3. **The bias in the labels is stated, not hidden.** A file declaring that support for a named entity is positive encodes a political stance. That is legitimate for a monitoring product and indefensible presented as neutral analysis, so it is labelled as the former in the schema, in the documentation and in this report.
@NUM|E4. **The system does not claim more than it did.** Provenance on every label; an explicit degraded-components list; a stub flag on every stored vector; an explicit vision status where only one value licenses a claim about an image. The evidence ledger in Table {{tab:evidence}} is the same commitment at the level of the whole project.
@NUM|E5. **Untrusted input is treated as untrusted.** Comment text is attacker-controlled. It is escaped before rendering, wrapped in data delimiters before a model sees it, and never permitted to alter a system instruction. This is risk reduction and is described as such: no prompt-level defence can promise resistance to prompt injection [43], and the tests do not pretend one does.

@P|One ethical limitation is stated plainly here rather than left implicit. The comments analysed here were published publicly but their authors did not consent to this analysis. The mitigations - aggregate reporting, tenant scoping, retention controls, and the refusal to attribute a label to a comment no model read - reduce the harm; they do not resolve the underlying question, which is a policy matter for whoever deploys the system rather than an engineering one.

@H3|5.2.4  Sustainability Plan

@P|**Technical sustainability** rests on the property that made the audit passes productive: a cross-component rename breaks a test rather than a feature. Stream names, consumer groups and label vocabularies each live in exactly one module; the deployment manifests are asserted against those modules; every repaired defect has a regression test; and a mutation pass confirmed that nine of ten of those tests actually fail when the fix is reverted. Test code is 35 percent of the repository, and the growth is almost entirely regression coverage.

@P|**Operational sustainability** rests on the backend being pluggable. An operator with accelerators runs everything in-house at zero marginal token cost; an operator without them runs the same code against a metered API and owns no hardware; an operator with a burst pattern does both. Because the switch is resolved per call, this is a configuration decision rather than a migration.

@P|**Economic sustainability** is addressed in Section 5.3. **Scientific sustainability** is the corpus: 10,272 real code-mixed comments with crowd reaction signals attached, together with a stratified sampler and a scorer, are ready for the annotation effort that would turn this engineering result into a benchmark result. That is the single highest-value piece of future work and it is human hours rather than compute.

@CHAPTER|6|Conclusion

@INTRO|This chapter summarises what was built and what was learned, states the project's limitations without softening them, and sets out the work that would close each one, in the order that would produce the most value.

@H2|6.1  Summary

@P|This project asked a narrow, testable question: given a post together with its comment thread, in a language setting that mixes Bangla script, English and romanized Banglish, can a system decide *per unit of work* how much intelligence that unit deserves, spend the expensive model only where cheap models cannot answer, and prove afterwards from its own counters where the money went and what produced every label?

@P|The answer is yes - and not in the way the project originally believed. A five-stage, queue-decoupled microservice was designed, built and measured. Cheap analysis runs on every post and every comment; a six-gate router decides post-level spend and a separate step decides which comments the expensive labellers read - two decisions rather than one, which is the structural change that made the cost behaviour measurable at all. Per-comment sentiment became eight independent labellers with explicit abstention, so a comment no model read reports as *uncertain* rather than as neutral. Watchlist stance answers whom a comment opposes at zero additional model calls, and nine tool-using agents reason over the system's own output through eighteen typed tools. Measurement then produced the key outcome of the work: **the routing gate behaves exactly as designed - 16 percent of posts route under the shipped engine against 74 percent for a keyword baseline - yet it governs only 30 percent of large-model calls, because between 85 and 96 percent of calls are comment-level and comment labelling runs for every post regardless.** That result contradicted the project's own headline claim and replaced it with a narrower one that survives contact with the data. Alongside it, hybrid retrieval reaches recall@10 of 0.8750 where hash-seeded vectors score 0.1875, and the whole system verifies as a single pass-or-fail chain in seventy-three seconds across 1,417 Python tests, 96 dashboard tests, lint, a production build and browser tests.

@P|The most transferable outcome is not any of those numbers but the discipline that produced them. Six independent audit passes established that the consequential failures in a system of this shape are not incorrect answers but **silent successes** - a gate reporting plausible behaviour while four of its six rules were inert, a retrieval arm matching zero rows while a passing test covered it, an inference server discarding eleven thousand prompt tokens and reporting only what it evaluated. The engineering response - named reader functions, single-source constants, provenance on every value, abstention instead of a default vote, and an evidence class on every published claim - is what this project would carry to the next system.

@H2|6.2  Limitation

@P|Six limitations bound what this report claims. The first five constrain the evidence; the sixth is a scope decision rather than a defect.

@BULLET|**L1 - The corpus is small and its comment sample is biased.** Fifty posts across twenty-five campaigns in a three-week window on one platform is a demonstration, not a study. The 10,272 comments are an engagement-ordered 3.75 percent slice of the 274,126 the platform reports, so thread-level aggregates describe *the most-engaged comments per post*.
@BULLET|**L2 - The multimodal claim is unexercised.** Forty-four of fifty posts carry images, and the image path - zero-shot visual sentiment [28], [29] plus optical character recognition - is implemented, but the 69 image references are object-storage keys whose objects are not present, so the image path has never produced a signal. Post sentiment is a text measurement, and the system reports an explicit failure status rather than a fabricated neutral verdict.
@BULLET|**L3 - Retrieval quality is measured against a machine-derived query set.** The 32 known-item queries were derived from each target post's own analysed topics and entities, with no human relevance judgement; that favours literal matching, marks exactly one relevant post per query, and leaves the decisive stratified bucket at eight queries.
@BULLET|**L4 - Scale is code-complete and unbenchmarked.** Horizontal scaling, queue-depth autoscaling and the Kubernetes deployment are implemented and test-asserted, but no multi-replica run has been timed or executed in a cluster, so every throughput statement is a design property rather than a measurement.
@BULLET|**L5 - The agent layer's answers are unmeasured.** The runner is hardened against six observed failure classes, each with a regression test, but groundedness, citation accuracy and answer relevance have no scores. The evaluation plan for them exists [44], [47] and has not been run.
@BULLET|**L6 - Labelling accuracy is outside the project's scope.** The sampler and scorer ship with the repository, but the gold file holds **zero adjudicated labels**, deliberately: seeding them from a model in this repository and then scoring that model would measure agreement with itself. No macro-F1, confusion matrix, calibration curve [48] or ship gate exists for any labeller.

@P|Three further constraints are recorded rather than left in a screenshot. The per-analysis event stream has a five-minute server-side ceiling, after which the Trace tab treats the close as a failure while the pipeline finishes correctly; the monitoring stack ships correct scrape configuration but **provisions no Grafana dashboards**, so the operator-independent path ends at the metrics endpoint; and the prompt-injection hardening is **risk reduction rather than a solution**, because no prompt-level defence can promise resistance [43]. All three are carried at that evidence class in Tables {{tab:features}} and {{tab:evidence}}.

@H2|6.3  Future Work

@P|The future work is ordered by value per unit of effort. The first item is the one this project deliberately scoped out, and it dominates the rest because most of the others depend on it.

@BULLET|**F1 - Adjudicate the gold set** (the bottleneck; everything else is fast). Two annotators labelling a five-hundred-comment overlap and reporting Cohen's kappa [49], then labelling to two or three thousand comments stratified by language bucket and comment kind, sampling *within* strata at random so the gold set does not inherit the corpus's engagement bias. The guideline must rule explicitly on sarcasm marked only by an emoji [17], conventional political epithets, single-word comments and mid-sentence code-switching. **This is the step that would extend the work from an engineering deliverable to an empirical one.**
@BULLET|**F2 - Benchmark rather than build.** With labels in hand, score the seven ensemble heads, the LLM stance pass and the Stage-1 baseline, reporting macro-F1 **per language bucket**; disable the response cache for every run and report provenance alongside every row, because a model that fell back to a heuristic has not scored on the whole set.
@BULLET|**F3 - Turn the cascade into a measured trade-off.** Sweep the router's confidence threshold and plot macro-F1 against cost and latency, with all-cheap and all-large as the endpoints. Because the gate governs only 30 to 55 percent of calls, plot the **comment-cap lever as a second curve** or state plainly that the sweep covers post-level spend only.
@BULLET|**F4 - Validate the watchlist separately**, on two metrics reported apart: mention detection - the precision and recall of the alias matcher, where recall is what matters because a missed alias is invisible - and stance agreement on the correctly matched mentions only.
@BULLET|**F5 - Learn the routing decision instead of hand-tuning it,** in the manner of the learned-router literature [31]. This is the most valuable upgrade to the mechanism itself, and it becomes possible only after F1, because a learned router needs labels to learn against.
@BULLET|**F6 - Make the image modality real, or delete its weights from the design.** Uploading the 69 image objects is roughly half a day and would turn an unsupported claim into a measured one; scoping the system permanently to text is equally defensible. What is not defensible is a weight that has never been anything but zero.
@BULLET|**F7 - Score the agent layer.** Build an analyst question set with reference answers and citing posts, and score groundedness claim by claim, citation accuracy, answer relevance and tool-use correctness with a judge model and human review on a sample [44], [45], [47], using the retrieval-specific measures of [46]. The run records already carry everything the scoring needs.
@BULLET|**F8 - Benchmark the scale claims.** Run a multi-replica deployment in a cluster against a ten-thousand-thread batch and record per-stage throughput and queue lag against replica count, converting NFR1 from a design property into a measurement.
@BULLET|**F9 - Close the two operational gaps the walkthrough exposed.** The trace view should resubscribe with a fresh ticket at the five-minute ceiling and distinguish "the stream ended" from "the run failed"; the monitoring stack should ship provisioned Grafana dashboards against the scrape it already configures.
@BULLET|**F10 - Have the access-control surface reviewed by someone who did not write it.** The 138 security tests are white-box tests written by the members who wrote the code they guard - exactly the class of assurance that a fresh-eyes pass repeatedly proved insufficient elsewhere in this project.

@P|Taken together, F1 through F4 would take the project from a demonstrable engineering result to a defensible empirical one, and the estimate is three to four weeks dominated almost entirely by annotation. Everything that used to sit in front of that annotation - the sampling frame, the cache key that would have compared a model against its own cached output, the caps that hid seventy percent of the corpus, and the labels that could not say what produced them - is now cleared.
